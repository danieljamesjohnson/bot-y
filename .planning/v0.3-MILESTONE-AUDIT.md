The alerting disjointness was verified structurally *and* by execution: `alerts` is a
comprehension over `results`, `_remembered_rows` selects by absence from `results`, so a
remembered row is never a `Result` and **cannot fire an alert** — confirmed with a synthetic
two-cycle run where a paced-out retailer published `availability: in_stock` from memory with
`alertable: false`.

Three behaviour changes to earlier-milestone code, all in the safe direction: Best Buy's
`salePrice` is type-coerced (a string price becomes `None` rather than `TypeError`);
`State.save` is wrapped (a failed write logs instead of aborting a cycle that already sent);
and `boty check` no longer commits `state.json`, so it can no longer silently spend a restock
transition it cannot send.

**Not measured, and stated as such:** no network requests were made during this audit, so
nothing here says the fetch layer still reaches any retailer today.

## The code review that ran after the close

A review of the phase's 17 changed files found **1 Critical + 8 Warnings**, all nine fixed.
The Critical was a reproduced XSS sink: `served/boty/index.html` interpolated `w.availability`
into a `class="dot ${...}"` attribute unescaped, reachable because `monitor._remembered_availability`
deliberately returns any string from `state.json` and 07-04 publishes it. The gate that should
have caught it listed `w.read_at` as untrusted and omitted `w.availability`, which arrives from
the same file by the same route. Both the sink and the gate were fixed.

That the phase shipped a bound which read like one and was not one, between 07-04 opening the
sink and the fix, is carried in criterion 5's qualification rather than erased.
