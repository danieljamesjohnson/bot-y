## The five criteria this phase is judged on (verbatim from ROADMAP.md, unedited)

  1. Two retailers whose intervals coincide are **not** dispatched inside the same short window; the bound is a stated number of seconds and is asserted on the schedule, never on a wall clock
  2. Each retailer's next-attempt time is **independent**: changing one retailer's interval or backoff moves that retailer's schedule and no other's, asserted in both directions
  3. Over a simulated day, the maximum number of retailers requested within any 60-second window is a **stated number**, and it is smaller than the current six
  4. **No regression in what already works**: per-retailer cadence and backoff still hold, and `boty check` — a deliberate full pass, which is a different thing from the daemon's schedule — still completes inside REQ-08's 2-minute budget, re-measured rather than assumed
  5. `make verify-offline` exits 0, with at least one new mutation registered and observed CAUGHT

**This plan owns the FIRST HALF of criterion 3 and nothing else.** The after-number, the comparison
and the word *smaller* are 09-02's. Criteria 1 and 2 are 09-02's; criterion 4 is 09-03's and 09-04's;
criterion 5 is 09-04's. `make verify-offline` is run here (Task 3) to prove the tree is still green
with a new test in it — that is a regression check, not criterion 5, and § *What this plan does not
claim* says so again where a reader will meet it.

## Rule 1's stated exception, in this plan's own words

This repository's standing rule is that **every gate is watched red before it is trusted**: run it
against the unfixed code, record the actual failure count, fix, record the pass. Task 1's stated
literal is the exception, and the exception is a finding rather than a skipped formality.

**There is no red to watch on the literal, because there is no defect it defends against.** A
watched-red gate works by pointing a new assertion at code that is currently wrong; the failure count
is evidence that the assertion has a subject. This literal's subject is the code *as it stands*. The
lockstep is not a bug being fixed here — it is the thing being measured. Writing a deliberately wrong
literal and watching `assert ==` reject it would prove that `assert ==` works and nothing else.

**What replaces the red-watch is four things that CAN fail and do have subjects, and three of them
are watched red in Task 1:**

1. the **denominator** assertion, which fails if the loop did not run a full day;
2. the **fleet** assertion, which fails if `config/products.yaml` no longer describes the fleet the
   number is about;
3. the **two independent tallies**, which fail if the events and the per-retailer counts disagree;
4. the fact that the literal is **transcribed from a run**, with the raw transcript pasted into
   `09-DECISIONS.md` — so the number is evidence rather than an expectation the test was shaped to
   meet.

And there is a red in this test's future, which is scheduled rather than absent: **09-02's change
turns it red.** That is collision C, resolved in Task 2. This test's second job is to be 09-02's
watched-red evidence for criterion 3.
