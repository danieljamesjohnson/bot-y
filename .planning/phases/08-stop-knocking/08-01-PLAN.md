**Purpose.** Criterion 3 asks for two stated numbers and a comparison between them. The second is
easy and the first is perishable: *"the total number of requests made to a retailer that never

## The six criteria this phase is judged on (verbatim from ROADMAP.md, unedited)

  1. After a bounded number of consecutive refusals, the wait returned for that retailer is measured in **days**, asserted against literal expected seconds — not against "greater than the old ceiling"
  2. A retailer in cool-off is requested **exactly once** when the cool-off expires, not once per cycle. The single-probe behaviour is asserted over a simulated sequence of cycles, not inferred from the interval
  3. The total number of requests made to a retailer that **never** recovers, over a simulated 30 days, is a **stated number** and is strictly smaller than the same simulation under the current rule. Both numbers are recorded
  4. A retailer that answers during its probe returns to its normal cadence **immediately**, and the cool-off state is cleared — the failure mode where a recovered retailer stays throttled is asserted against
  5. The cool-off **survives a restart**, the same guarantee the existing backoff already carries, and is discarded when stale by the existing rule rather than a second one
  6. `make verify-offline` exits 0, with at least one new mutation registered, observed CAUGHT, and anchored on **behaviour** rather than on message text

**This plan owns the FIRST HALF of criterion 3 and nothing else.** The `after` number, the
comparison, and the word *strictly* are 08-02's. Criteria 1, 2 and 4 are 08-02's; criterion 5 is
08-03's; criterion 6 is 08-04's. `make verify-offline` is run here (Task 3) to prove the tree is
still green with a new test in it — that is a regression check, not criterion 6, and § *What this
plan does not claim* says so again where a reader will meet it.

## Rule 1's stated exception, in this plan's own words

This repository's standing rule is that **every gate is watched red before it is trusted**: run it
against the unfixed code, record the actual failure count, fix, record the pass. Task 1 is the
exception, and the exception is a finding rather than a skipped formality.

**There is no red to watch, because there is no defect this test defends against.** A watched-red
gate works by pointing a new assertion at code that is currently wrong; the failure count is
evidence that the assertion has a subject. Task 1's subject is the code *as it stands*. The current
rule is not a bug being fixed here — it is the thing being measured. Writing a deliberately wrong
literal and watching `assert ==` reject it would prove that `assert ==` works and nothing else, and
dressing that up as a red-watch would be exactly the rounding-up this repo forbids.

**What replaces the red-watch is three things that CAN fail and do have subjects:**

1. the denominator assertion, which fails if the loop did not run the full 30 days;
2. the two independent tallies, which fail if the count and the schedule disagree;
3. the fact that the literal is **transcribed from a run**, with the raw transcript pasted into
   `08-DECISIONS.md` — so the number is evidence rather than an expectation the test was shaped to
   meet.

And there is a red in this test's future, which is scheduled rather than absent: **08-02's change
turns it red.** That is collision C, resolved in Task 2. This test's second job is to be 08-02's
watched-red evidence for criterion 3.
