<objective>
Write the durability rule down, number it, and apply it to every control this project ships — naming
every failure, including the ones nobody wants named.

**Purpose.** The rule is already half-written. `docs/adding-a-retailer.md` § *The rule a control has
to satisfy* says: *"first-party, evergreen, restocked routinely, never the subject of a buy-box
fight, and not a console."* It has **never been applied to anything in writing**, and nothing gates
it — so the tree quietly violates it: **GameStop's control is a PS5 console**, which the rule's own
last clause forbids and which `config/products.yaml`'s Walmart block argues against in prose two
hundred lines away.

The ROADMAP names the clause the sentence is missing: *Best Buy's died because it was a specific game
SKU; a control that can be discontinued eventually will be.* "Evergreen" gestures at that and does
not state it, and a gesture is not a rule you can apply to a candidate.

**Criterion 4 is not "choose a better control".** It is *the rule … is written down and applied to
every existing control, with any control failing it named.* Expect it to condemn more than one.
**Naming them is the deliverable, not a failure**, and a rule that condemns nothing after being
applied to six controls chosen before it existed is a rule that was fitted to them.

**Output.** Numbered clauses extending the existing sentence rather than replacing it; a verdict per
clause for all six controls; every failure named; and a gate that makes the naming un-droppable.
</objective>

  <action>
Turn the existing sentence into numbered clauses, in the dated-reversal form this repository uses:
**quote the original whole, keep it, then state what this phase's evidence adds and why.** The
sentence is not wrong. It is incomplete, and the incompleteness has a measured cost — a control died
and the monitor reported the death as its own failure.

Ship five clauses. The outline's cut is the starting point; you may re-cut or rename them and must
defend whatever you ship at the site. **You may not drop one to make a control pass.**

- **first-party by construction** — sold by the retailer's own entity or house brand, so no buy-box
  rotation can take the listing away. This absorbs two of the original clauses and says why they were
  one idea.
- **replenished, not released** — a consumable or evergreen catalogue staple, restocked routinely;
  never a unit with a launch date and an end of life.
- **not generation-bound** — its existence does not depend on a hardware or software generation the
  manufacturer will end. **This clause is new**, it is the one Best Buy's control failed, and the
  ROADMAP's sentence is its justification. It is also the clause that generalises the original's
  *not a console*: a console is the archetype of a generation-bound product, not the whole of it.
- **a recorded reserve candidate that itself passes the clauses above** — the document already asks
  for a fallback and already names Nintendo's; this makes it a clause and, crucially, checks the
  fallback against the rule instead of merely requiring one to exist.
- **its death is legible** — when the target stops resolving, the monitor reports a dead control
  rather than a refusal or a broken detector. **Nothing in this repository satisfied this before
  `10-01` and `10-02`**, which is why it is a clause and not an assumption, and it is the clause that
  makes the rule survivable: no identifier is immortal, so the last question is what happens when one
  dies.

Give each clause a stable identifier the applied table and the gate can both cite. Keep the two
worked examples the section already has — the rejected Amazon HDMI cable and Nintendo's reserve — and
attach each to the clause it illustrates, so the clauses arrive with evidence rather than as
assertions.

**Satisfy the contributor-docs gate rather than loosening it.** No line-numbered citations, every
cited path real, the pinned headings intact. If a new heading needs pinning, extend the pinned list
in `tests/test_contributor_docs.py` — that is the gate being taught the new shape, which is different
from the gate being weakened, and the SUMMARY must say which one happened.

**In `docs/adding-a-retailer.md`: one table.** One row per control, one column per clause, one verdict
per cell, and a named reason in every failing cell. Not a summary sentence — the criterion says
*applied to every existing control, with any control failing it named*, and a table is the only form
in which "every" is checkable by eye and by machine.

**In `config/products.yaml`: one verdict line beside each control entry**, citing the clause
identifiers it fails, so the person editing the config meets the verdict where the decision is made
rather than in a document they may not open.

**Get the control set from the LOADER, and state the real count once you have it.**
`grep -c 'control: true' config/products.yaml` returns **7** and there are **6** — the seventh match
is a comment on the transition watches saying they are deliberately *not* controls. Load the config
the way `tests/test_config.py` does, filter on the same attribute `control_check.py` and
`assess_health` filter on, and write the number down from that. A count taken off the file rather
than off the configuration is the same class of error as a gate that greps a comment, and this task
is where it would enter.

**Measure each control against the shipped clauses. Do not copy the outline's predictions** — they
are predictions, written down in advance so that a softer finding would be visibly softer. Where your
verdict differs from the prediction, say so and say why; that is a finding about the rule.

Three things this task must get right rather than glide past:

1. **A reserve candidate is checked against the rule, not merely counted.** Best Buy's recorded
   reserve in `docs/retailer-evidence.md` is another title in the same class as the control that
   died, and Nintendo's is another accessory of the same generation. A fallback that fails the same
   clause as the thing it replaces is not a fallback, and saying so is the clause earning its place.
2. **The Walmart control's pin is not a durability failure and is not silently ignored either.** Its
   product passes the product clauses. The pin itself is **set on disk since 2026-08-25 and not yet

   test. Cite that test by name so the verdict rests on a gate rather than on this sentence.

life of the project. That is not an accusation, it is the argument for Task 3: an unapplied,
ungated rule is a rule that is already being broken.

**Nothing in this task changes a control.** Every failure is recorded as **named and unrepaired**.

Write the gate that makes the application un-droppable. Two directions, because a one-directional
gate rots the moment somebody adds something:

- **every control the config LOADER yields appears in the applied table with a verdict against every
  clause the document declares** — a control added later with no verdict reddens. Load it; do not
  grep it. A grep over this file counts a comment that says the transition watches are deliberately
  not controls, so a grep-based gate would demand a verdict for a watch that has none to give;
- **every clause the document declares has a verdict in every row, and every row in the table is a
  control the config actually configures** — a clause dropped from the document, or a table row for a
  control nobody watches, reddens.

Derive the clause list **from the document** rather than hard-coding it in the test. A gate that
carries its own copy of the rule is a second place for the rule to live, and the two only have to
disagree once. Hard-coding the clause identifiers would also make Task 1's "you may re-cut them"
false.

**Watch it red in both directions, on a copy, before trusting it.** On the `test_support_matrix.py`
precedent: run the same rule against a deliberately broken copy of each input rather than against the
real tree. Record the actual failure count for each:

1. a control entry with its verdict removed;
2. a clause removed from the document;
3. a table row for a control that is not configured.

If one of them cannot be made to fail, that is a **finding** and is written down as one — a gate
nobody has watched fail is not a gate, and this repository has shipped exactly that mistake before
in `scripts/evidence_check.py`'s predecessor, which is documented in that file's own header.

**Then run the whole suite** and record the result, including whether the new module changed any
collection count elsewhere.
