<objective>
Make the store a fact that exists and is visible.

`Watch.store_id` lands as a per-watch pin in `config/products.yaml` with no default.
`Result.store` records which store the page said answered, read off a pinned
`__NEXT_DATA__` path. Both reach `status.json`, `boty check` output and the dashboard
row. And the leak hole this opens is closed **first**, in the same plan:
`scripts/identity_check.py` is measurably blind to the `store_id:` YAML spelling — the
exact key REQ-14 puts into a tracked, public file.

**Purpose.** On 2026-08-09 the daemon recorded the Walmart milk control `OUT_OF_STOCK` at
$3.17 while three live reads minutes later returned `IN_STOCK` at $2.42. Same URL, same
parser. A parser bug does not change a price — two different stores answered. Today a
Walmart reading is a statement about an arbitrary store and nothing in the system can even
say which one. This plan makes it say.

**Output.** A widened identity rule watched going red, `Watch.store_id`, `Result.store`,
`parse.nextdata_store`, two new `status.json` keys, one dashboard tag, one `boty check`
tag, and `store_id` on both Walmart watches.

**NOT in this plan, and the executor must not reach for it.** *No verdict changes.*
Nothing here turns an unpinned or mismatched store into `Availability.UNKNOWN`, and
`_verdict_from_html` must not branch on `store` or `store_id` at all. That guard, its
health message and its mutations are **05-02**, and this plan exists so 05-02 has a fact
to guard on. Making the store recordable and readable is the whole scope. Criterion 2's
"unset means UNKNOWN with a health message saying so" is split deliberately: the *config*
half (a per-watch `store_id`, no default) is here; the *verdict* half is 05-02.
</objective>

**`scripts/identity_check.py` — the YAML/config carrier, watched going red.** Measured on
this tree 2026-08-10: `'  store_id: 12345\n'` → `[]`, `'  store_id: "12345"\n'` → `[]`,
`'    storeId: 202\n'` → `[]` and `'  STORE_ID: 12345\n'` → `[]`, while `'store_id=12345'`

Add a **new entry to the `keyed` tuple** — a carrier column, not another key spelling, the
same move the cookie and `data-` attribute rules made. The pattern, with the classification
string `"store number in a config key"`:

`(?m)^\s*[A-Za-z_]*[Ss]tore(?:_?[Ii][Dd]|_?[Nn]umber|_?[Nn]o|_?[Cc]ode)?\s*:\s*"?(\d+)`

**The character classes in that pattern are load-bearing and must not be simplified back to
`[a-z_]*store(?:_?id|_?number|_?no|_?code)?`.** The lower-case-only form was measured and it
does **not** catch `storeId: 202`: `[a-z_]*` matches `store`, the optional suffix group
cannot match a capital `Id`, so `\s*:` is tested against `I` and fails. The `keyed` loop does
pass `re.I`, which would paper over it — but a pattern that is only correct because of a flag
its caller happens to apply goes silently wrong the moment anybody moves or reuses it, and
this file already carries two comments recording `re.I` being dropped as a silent mutation.
As written the rule catches `storeId` **on its own**; `re.I` additionally buys the
SCREAMING_CASE spelling, which is measured above rather than assumed. Put that reasoning in
the comment.

**Measured with the rule spliced into `keyed` and `--all` run over the whole tree,
2026-08-10:** `identity check: PASS — 168 file(s)`, exit 0 — **0 hits on the existing
corpus.** It catches `  store_id: 12345`, `  store_id: "12345"`, `    storeId: 202` and
`  STORE_ID: 12345`, and does **not** fire on `  store_id: ${WALMART_STORE_ID}`,
`  state_path: state.json` or `  status_path: served/boty/status.json`. The `^\s*` anchor
under `(?m)` is what keeps it off prose and off the JSON forms the existing rules already
own. Comment it with the measurement and the date, in the block's established voice.
