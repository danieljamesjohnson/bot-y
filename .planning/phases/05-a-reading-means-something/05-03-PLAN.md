<objective>
Make the backoff outlive the process, so "pushed once after the cap" means once.

`Pacer._state` is in-memory today. A service restart resets every refusal count to zero,
which does two separate kinds of damage: the backoff climbs again from 2x instead of
resuming at its real depth, and the page-once bookkeeping that hangs off it re-pages a
retailer somebody was already told about. REQ-16 says a refusal that outlasts the cap is
pushed **once**. Today it is pushed once *per process*.

**This is persistence plus a restart-level test, not new push logic.** `cli.watch_cycle`
already implements all three of REQ-16's clauses — `log.info` for a refusal the backoff is
handling (recorded, not pushed), `warned` for pushed-once, `_refusal_is_entrenched` for
outlasts-the-cap. The outline measured that and this plan is weighted accordingly. Criteria
5 and 6 are one change.

**Purpose.** STATE.md has carried a standing instruction since 2026-08-04: *do NOT restart
`boty.service` while a retailer is in backoff.* A daemon you cannot restart without
undoing its politeness is a daemon that runs stale code, and it has been running
pre-Phase-4 code since 2026-08-04 17:48 for exactly that reason. 05-04 restarts it, and it
is safe to do so **because this plan ships**.

carrying the reversal; a `pacer_state_path` setting; a `.gitignore` line; the paging memory

*across* a restart.

## The one measurement this plan is built on: `due_at` is unpersistable

`boty/pacing.py:114` sets `st.due_at = now + wait`, where `now` is whatever the caller
passes. `boty/cli.py:313-317` is that caller, and it passes `scheduled_now` — a synthetic
clock the loop advances by the delay it *asks* for, with the comment already explaining
why (deterministic under a fake sleep in tests, accurate in production). **It starts at
`0.0` in every process.**

So a persisted `due_at` is a number with no referent after a restart. Compared against a
fresh `scheduled_now` of `0.0` it either fires immediately (if it was small) or blocks a
retailer for the entire age of the previous process (if it was large). Neither is a
schedule; both are an accident.

`cli._refusal_is_entrenched` (`cli.py:192-196`) reads `refusals` and nothing else.
**`refusals` is the field criterion 6 actually needs.** Persist that plus a wall-clock
stamp; let `due_at` rebuild from zero. Say it in the code, not only here.

**`Pacer.load(self) -> set[str]` and `Pacer.save(self, warned: set[str]) -> None`.**

The signatures are the one non-obvious decision in this task and they must be argued in
the method docstrings, because a reviewer will otherwise read `warned` as a field this
class forgot to store:

- `warned` is **passed through, never held**. `Pacer` decides cadence — `due`, `record` and
  `skipped_reason` do not read it and must not start. `cli.watch_cycle` decides paging. But
  the two facts are written and read at the same moments and REQ-16's *"pushed once"* is a
  joint property of both — `refusals` decides whether a refusal is *pageable*, `warned`
  decides whether it has *already been paged* — so restoring one without the other restores
  half a decision. One document, one write, one load; a second file would be a second
  gitignore line, a second corrupt-file path and a second way for a restart to come back
  with a contradiction. A field the class never reads would be a smell; a parameter it only
  serialises is a stated pass-through.
- Instance methods, not a `State`-style `classmethod`. `Pacer` needs `default_interval` and
  `overrides` at construction, and `cli.py:308-309`'s invariant — *"one pacer for the life
  of the loop"* — means the loop builds the pacer and then loads into it. A classmethod
  would invite a second construction site, which is the thing that invariant forbids.

`load` copies `monitor.State.load`'s shape (`monitor.py:40-45`) and `nextdata_offers`'
discipline: one `try` around the read and the parse catching `(OSError,
json.JSONDecodeError)` into empty state, and `isinstance` at **every** step inside it, each
returning nothing rather than guessing, so no other exception type can arise from a hostile
document. A corrupt, absent or hostile file must never stop the monitor starting — that is
the whole of T-05-04, and the behaviour list drives a table of malformed documents through

a dict; `refusals` is an `int` and not a `bool` (`bool` is an `int` subclass — `_price`'s

`time.time() - refused_at` lies in `[0, STATE_MAX_AGE_SECONDS]` — **both** bounds, because
a future stamp is a clock that jumped backwards and would otherwise hold the state forever.
Clamp the restored count to `MAX_PERSISTED_REFUSALS`. Build each restored
`_RetailerState` with `interval` taken from `self.overrides` / `self.default_interval` —
never from the file — and say why: the interval is a config decision, and a persisted copy
would let yesterday's file quietly override an edit to `retailer_intervals`, which is the
opposite of what a settings file is for. Do not read `due_at` under any circumstances.

`save` writes `{version, retailers: {name: {refusals, refused_at}}, warned: [...]}`, with
`sort_keys=True` and `indent=2` on `State.save`'s precedent, and **omits every retailer

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the persisted pacer state file → `Pacer` at daemon start | Untrusted deserialisation with a local writer. The file is written by this process and read by the next one; between those two moments it is an arbitrary sequence of bytes on a disk that can fill, be truncated by a power loss, or be edited. |
| the file's `refusals` integer → `record`'s `BACKOFF_FACTOR ** refusals` | A number out of a file reaching an arithmetic expression with a domain limit. |
| the file's `refused_at` stamp → the host wall clock | An external, adjustable reference. NTP corrections and manual clock changes move one side of the comparison. |
| the restored `warned` set → `watch_cycle`'s paging decision | A file now decides whether a human is told about a refusal. Restoring it wrongly either silences a page that was due or repeats one already sent. |

| T-05-04 | Denial of service | the persisted pacer state at daemon start — `Pacer.load` | mitigate | The headline threat this plan owns, sharpened into T-05-12 through T-05-15 below.
