<objective>
Close the phase: make the runtime budget measurable rather than assumed, wire the
honesty gate into `make verify` so it outlives this phase, complete the support
matrix, and prove all of it under the environment the service actually gets.

Three things this plan exists to prevent, each of which has already happened once
in this project:

1. **A number nobody measured.** REQ-08 gives a two-minute budget and the only
   figure anyone has is 40 s from 02-04's summary, taken by hand. If a rung-3
   retailer landed in 03-02, the cost of a browser render is what could blow
   that budget — so publish the elapsed time and read it, rather than asserting
   it.
2. **A gate that has gone vacuous.** 03-01 built `scripts/evidence_check.py`
   because Phase 2's count clause is now satisfied by documents that predate
   this phase. A gate that only runs inside one plan's `verify` block dies with
   the plan; this one has to run in `make verify` forever.
3. **A green that was measured in the wrong environment.** 02-03 shipped a
   `make verify` that passed in a shell with `BOTY_BROWSER_PATH` exported while
   the service could not find Chrome, and paged Dan half an hour later. Every
   live claim in this plan is made under `systemd-run` with the unit's own
   `EnvironmentFile`.

And one thing this plan is the last chance to close: `02-VERIFICATION.md` left
CR-01 durability open as a human item, because a one-shot `make verify` cannot
measure a daemon-lifetime property and the three teardown tests drive a *fake*
nodriver. Only elapsed time closes it, so this plan spends some.

Purpose: REQ-07 and REQ-08, and phase criteria 3, 4, 5, 6 and 7.

Output: a published, measured check duration; the honesty gate running inside
`make verify`; a complete support matrix with an offline test behind it; and a
recorded, honest answer to "does `boty check` report five or more retailers" —
including the answer "no, and here is why", if that is the truth.
</objective>

<design>
**How the duration is published.** `boty.status.write(path, results, health)`
gains a keyword-only `duration_seconds: float | None = None`, serialised as a
top-level `duration_seconds` key. The default keeps every existing call site
valid and means "nobody measured this pass" rather than "it took no time" — the
same three-valued honesty `Availability` is built on, applied to a number. Both
callers time the `run_once` call and pass the result: `cli.main`'s check branch
and `cli.watch_cycle`. Timing `run_once` rather than the whole process is
deliberate: process startup and config load are not what REQ-08 is about, and a
number that drifts with Python's import time is not a retailer measurement.

Use `time.monotonic()`, not `time.time()` — a wall clock that steps backwards
during an NTP correction would publish a negative duration, and this file is
served over HTTP.

The dashboard contract in `boty/status.py` says these keys are read verbatim by
the page. Adding a key is additive and `served/boty/index.html` needs no change
for this plan; note in the comment that the key exists so REQ-08's budget can be
read rather than re-measured by hand.

**Where the budget assertion lives, and where it does not.** Not in `make
verify`: the live control stage already spends real time and duplicating a full
check would add ~40-70 s to every run, for a property that changes only when the
config does. The assertion is a read of the published `duration_seconds` after a
real run, which is what task 3 does. The published number is the durable part.

**If the measurement exceeds 120 s.** The answer is not "delete a watch".
Permitted remedies, in this order, each requiring evidence in the summary:

  1. Reduce `settle_seconds` on a rung-3 call where a capture proves the page is
     complete sooner. Per-call, evidence-backed, not a global default change.
  2. Reuse one browser process across the renders in a single pass. Chrome
     startup is the dominant cost of rung 3, so this is the real fix — but it
     touches `boty/browser.py`'s teardown, which is CR-01 territory. Only
     attempt it with the teardown tests green, and take a live zombie reading
     afterwards. If that is more work than this plan can hold, record it as a
     finding for Phase 4 with the measured number, rather than half-doing it.
  3. Narrow `boty.fetch.get`'s per-request jitter floor. Last resort, must be
     recorded, and must not violate the polite-polling non-functional
     requirement.

Forbidden, explicitly: removing or disabling a watch, dropping a control, or
un-configuring a retailer to make the number fit. If the budget cannot be met
without one of those, REQ-08 is unmet — record the measured number, say so, and
escalate. A monitor that hits its runtime budget by watching less is not one
that hits its runtime budget.

**Why the count assertion cannot be a one-liner this time.** 02-04's clause was
"five or more retailers, OR `rung 4` in QUESTIONS.md and `**Verdict: REFUSED**`
in docs/retailer-evidence.md". Both of those strings are in the tree already,
from Pokémon Center, so that clause can no longer fail. 03-01 replaced it with
`scripts/evidence_check.py`, which checks per-retailer sections and restricts the
configured set to the roadmap's seven. This plan's job is to put that script
inside `make verify` — via a test in the offline suite, not a new Makefile stage,
because the Makefile's stage list and its four exit codes are pinned by
`tests/test_verify_makefile.py` and a new stage would be a large change for no
extra signal.

**The support matrix gate.** Criterion 3 requires DEGRADED in the matrix *and*
in `boty check`. The runtime half is already pinned (`Result.degraded` derived
from rung, mutation M6, `test_a_browser_reading_serialises_as_degraded`, and
`tests/test_dashboard.py`). The matrix half is prose in `README.md` and nothing
checks it, which is exactly how WR-04 shipped a contract asserted at the
producing end and unimplemented at the consuming one. So it gets a test.

**The daemon-lifetime reading.** `02-VERIFICATION.md` human item 2, verbatim:
leave the service running, then count zombie children of the main PID and `uc_*`
directories inside the unit's private tmp, twice, hours apart, expecting zero of
both and **flat** between readings rather than merely low. The original leak
reached 13 zombies and 204 MB in 71 minutes at roughly one per 5-minute cycle,
so 40 minutes and 6 completed cycles is a real signal, and the unit sets
`PrivateTmp=true`, so its profiles land under
`/tmp/systemd-private-*boty.service*/tmp/` rather than in the host `/tmp`. Take
the second reading *before* anything in this plan restarts the service, or the
window resets and the reading means nothing.

**Every live claim runs under the service's environment.** The browser path is
configured in `/home/dan/.config/boty/env`, not in any shell profile, so a green
obtained in an interactive shell says nothing about the deployment. Use
`sudo systemd-run --pipe --quiet --uid=dan --property=EnvironmentFile=/home/dan/.config/boty/env --property=WorkingDirectory=/home/dan/CodeProjects/pokemongoplusplus <command>`.
`boty check` writes `state.json` and the served status file through `run_once`,
so stop `boty.service` before running it by hand and restart it afterwards
rather than racing a live cycle.

**Three `make verify` verdicts, and only one of them closes this phase.**
`VERIFY: PASS` is the criterion. `PASS (OFFLINE)` means no live control ran.
`PASS (INCOMPLETE)` means some control could not run on this host — which, under
the service `EnvironmentFile`, would mean the deployment cannot reach a detector
it is configured for. Neither qualified verdict satisfies criterion 7; record
which one appeared if either does.
</design>
