<design>
**The hazard specific to Target, and it is already in the shipped code.**
`boty/retailers.py` line 31 already carries `"target": {"target"}` in
`FIRST_PARTY`, and line 54 already lists `target` in `MARKETPLACES`. That
combination is live today for any Target watch and it has a sharp edge: if
Target's markup attributes an offer to a seller string that is not exactly
`target` once lowercased and stripped — `"Target"` is fine, `"Target
Corporation"` or `"Target.com"` is not — then `_pick`'s `named` list is empty,
the `unattributed` list is empty because `target` is in `MARKETPLACES`, and
`_verdict_from_html` falls through to the final branch (`boty/retailers.py:177`)
and returns a **confident `OUT_OF_STOCK`** with detail "N offer(s) via ld+json,
none first-party" on a page it could read perfectly.

**Be precise about how loud that failure is, because it decides which safeguard
is load-bearing.** It is *not* silent. `boty.monitor.assess_health:78` fails any
retailer whose control does not read IN_STOCK, so seller-string drift on the
Target control raises a health warning, reddens the `controls` stage and takes
`make verify` non-zero. The control/health path **is** the drift detector, and it
already works. What the allow-list entry buys is that Target reads correctly in
the first place rather than being permanently red; what the test buys is that
the OUT_OF_STOCK-for-a-third-party behaviour stays deliberate rather than
becoming accidental.

So: read the live `offers.seller.name` from real bytes, record it in the evidence
doc, and widen `FIRST_PARTY["target"]` to contain it. Do not guess it from the
fixture's prose, and do not soften the third-party verdict to UNKNOWN to make a
mismatch hurt less — "Target itself is not selling this" is a true stock fact,
which is exactly what `test_a_configured_retailer_still_reports_out_of_stock_for_a_third_party_offer`
(`tests/test_retailers.py:256-272`) pins for Walmart.

**Target Plus is a real marketplace**, so `target` stays in `MARKETPLACES` and
`_pick`'s unattributed-offer fallback stays disabled there. Do not "simplify" by
removing it — an unattributed offer on Target is genuinely "I do not know whose
this is", which is UNKNOWN territory, and a $229 flip listing is the thing on the
other side of that decision.

**Akamai fronts Target, and `BLOCK_PHRASES` was extended for exactly this.**
`boty/fetch.py` now carries `sec-if-cpt-container` and
`scf-akamai-protected-by`, both re-verified against live Kohl's bytes in Phase 2
precisely because Phase 3 walks the ladder at an Akamai-fronted retailer. So a
Target refusal at HTTP 200 should surface as `Blocked` with the matched phrase,
not as "no structured stock data found (page shape changed?)". If it surfaces as
the latter, that is a defect in our marker list rather than in the extractor, and
it gets recorded with the bytes the way the Kohl's re-probe was — do not debug
the parser.

**Do NOT add `datadome` as a block phrase.** `03-CONTEXT.md` locks this: real
product pages reference DataDome assets while serving genuine content, and
another project had to revert exactly that false positive. If a DataDome tell is
ever wanted, `captcha-delivery.com` together with the `var dd={` marker is the
safer pair.

**A browser is not a strict upgrade.** The same headless Chrome that reads Best
Buy is served a Cloudflare wall by gamestop.com, which rung 1 reads on every
`make verify`. Escalate to rung 3 because a page genuinely needs JavaScript or
refuses HTTP at the connection layer — not because one fetch failed.

**If rung 3 is where Target lands, it needs a generic browser checker, not a
contorted Best Buy one.** `check_bestbuy_browser` is Best Buy-shaped: it goes
through `bestbuy_product_url`'s SKU-search redirect and binds the verdict to a
SKU node. Target is addressed by URL, so the right addition is a small
`check_html_browser(watch, *, first_party_only)` beside `check_html` that fetches
`watch.target` through `fetch_rendered`, maps `Blocked` and `FetchError` to
UNKNOWN with `_redact_host_paths` applied to the detail, and calls
`_verdict_from_html` with `rung=Rung.BROWSER`. Then one arm in
`boty.cli._make_checker`. Two reasons that dispatch must go in `_make_checker`
and nowhere else: `scripts/control_check.py` builds its checker with the same
function, so a gate that routed differently would prove something about a code
path nobody runs; and `check_html` hardcodes `Rung.TLS`, so a browser reading
routed through it would be published as a first-class TLS reading and the
support matrix would be quietly wrong about the one retailer it is most careful
about.

**The offline network guard covers the browser seam by name.**
`tests/conftest.py` patches `boty.browser._render`. A new checker must reach the
browser through `boty.browser.fetch_rendered` (imported into `retailers` the way
`check_bestbuy_browser` imports it) so the guard still holds. If a test needs a
transport the guard does not patch, extend the guard rather than working around
it.

**Rung-3 captures leak the capturing host's identity.** Phase 2 froze this
repo's public IP and Akamai EdgeScape geolocation into a committed fixture in a
public repo. Target is Akamai-fronted, so it is the *same* echo shape and
`test_no_fixture_leaks_the_capturing_hosts_identity` already knows those markers
— but the guard only knows the markers it was taught, and a new page can echo
client identity in a form nobody has seen. Every new rung-3 fixture is suspect
until checked by hand as well as by the guard.

**Politeness, and the reason it outranks this retailer.** Dan's monitor is green
and notifying from this host's IP right now. A block costs him the working
monitor, which is worth more than Target. Hard limits for this plan: at most
**12** requests to any `*.target.com` host across every task, at least **15 s**
apart, a **120 s** backoff before the single permitted retry of any refusal, and
a hard stop after two consecutive refusals at the same rung. Run
`.venv/bin/python scripts/control_check.py` before the first probe and after the
last, and record both. If any pre-existing retailer goes red during this plan,
stop everything and report it — that is collateral damage, not a Target finding.

**Do not alter the `no structured stock data found` return text or its twelve
spaces of indentation.** `scripts/mutation_check.py` M2 anchors on that exact
source substring; drifting it takes `make verify` down as a HARNESS ERROR that
looks nothing like its cause. Run `make mutation` after any edit to
`boty/retailers.py`.

**Control selection**, from the rule in `config/products.yaml`: first-party,
restocked routinely, never a marketplace buy-box fight, not a console and not a
limited drop. On Target that means an owned-brand staple — Good & Gather, up&up,
Market Pantry — rather than a Nintendo product. Keep a reserve candidate, the
way the Best Buy row does, because "this product page renders" has not been
predictable at every retailer this project has probed.
</design>
