<objective>
Make the retailer's current cadence a number, and make both surfaces read the same one.

The backed-off interval is computed inline at `pacing.py:242-245` and discarded into `due_at`. This
plan extracts it into `Pacer.current_interval(retailer)`, has `record` compute its own wait through
that accessor, threads it into `status.write` the way `paced` is threaded, and gives `boty check` a
**load-only** `Pacer` so the surface criterion 3 names by name cannot answer differently from the
daemon.

**Purpose.** Criterion 3 says a reading is stale when it is older than **its retailer's current
interval** — "derived from the retailer's own pacing rather than a fixed clock". That number exists
nowhere today. `_RetailerState.interval` is the standing config value, unchanged by backoff;
`skipped_reason` returns prose; and the backoff-multiplied figure lives for four lines inside
`record` before being folded into `due_at`, which is a **synthetic-clock** number that restarts at
0.0 every process and is deliberately never persisted. So criterion 3 has had no source to compare
against. This plan creates it, and creates exactly one of it.

**Output.** `Pacer.current_interval`; `cli._current_intervals`, the single reader both surfaces go
through; one new `status.json` key on the `retailers` array; a load-only pacer on the check path
under three stated constraints; one new mutation, watched going red by hand before the harness ever
ran it; and a test that the fetch schedule did not move.

## The five criteria this phase is judged on (verbatim from ROADMAP.md, unedited)

  1. Every `Result` records when it was read, and that time is published per watch in `status.json`
  2. A reading with no recorded time is shown as UNKNOWN age, never as current — watched going red
  3. A reading older than its retailer's current interval is presented as stale in `status.json`, `boty check` and the dashboard, and the staleness is derived from the retailer's own pacing rather than a fixed clock
  4. The age survives a service restart, so a restart cannot make a two-day-old reading look fresh
  5. `make verify-offline` exits 0, and every gate this phase adds has been watched going red

**This plan owns the THRESHOLD half of criterion 3.** The row that can be old is 07-04's; the three
renderings are 07-05's. Criterion 5 binds here as the red-watch on M33.

## WHY THIS IS STRUCTURAL AND NOT CHEAP, MEASURED

`boty check` builds **no `Pacer` at all** (`cli.py:587-596`: `run_once(cfg.watches, checker, state)`).
So the cheap version of criterion 3 — let each surface work out the cadence for itself — makes
`boty check` compare a reading against `cfg.interval_seconds` while the daemon compares the same
reading against `cfg.interval_seconds * 2**refusals`. **Two surfaces publishing different staleness
verdicts about one reading is this project's own defect one level up**, and it is the defect REQ-21
exists to close, rebuilt on the surface the criterion names.

Measured on this host today, from the live `pacer-state.json` (version 2) and
`config/products.yaml`:

```
retailer   refusals   standing    CURRENT cadence
bestbuy       0         300 s        300 s
nintendo      0         300 s        300 s
gamestop      0         900 s        900 s      (override)
amazon        2        1800 s       7200 s      (override, x4)
target        7         300 s      21600 s      (the 6-hour cap binds)
walmart       7         300 s      21600 s      (the cap)
```

Six retailers, and the two surfaces would disagree about four of them by factors of up to 72. The
number they must agree on is the right-hand column, and today nothing anywhere prints it.

## SO: ONE NUMBER, ONE READER, AND THE SCHEDULE GOES THROUGH IT

Two joins, and both are structural rather than conventional:

1. **`record` computes its wait by calling `current_interval`.** The accessor is not a second copy
   of the schedule's arithmetic — it *is* the schedule's arithmetic, and `record` becomes a caller.
   A future edit to the backoff cannot move the published number away from the real one, because
   there is only one expression to edit. This is the derive-don't-store argument this module already
   makes twice (`STATE_MAX_AGE_SECONDS`, `pacing.py:113-123`) and `models.py:460-462` makes a third
   time.
2. **Both surfaces go through `cli._current_intervals(cfg, pacer)`.** Not "each surface builds the
   same dict"; one function, two call sites. `boty check` gets a `Pacer` built from the same three
   config values and `load()`-ed from the same document, so it reconstructs the daemon's own depth
   exactly — `refusals` is persisted and `interval` comes from config, which is why criteria 3 and 4
   agree rather than fight.

## THE THREE CONSTRAINTS ON THE CHECK PATH'S PACER, EACH A DEFECT IF MISSED

1. **Load-only. It must never `save()`.** `boty check` is routinely run while the service is
   running. Two writers to one document is precisely the contradiction `pacing.py:277-297`'s own
   argument against a second file exists to prevent, pointed the other way.
2. **It must NOT be passed to `run_once`.** That would make `boty check` skip watches — a behaviour
   change nobody asked for, and it would import Finding 4's vanishing rows onto the one surface that
   shows all of them.
3. **A missing `pacer-state.json` is the standing interval, not an error.** On a fresh clone
   `refusals` is 0 everywhere and the answer is the config value. It must not warn.

All three are asserted in Task 3, not described.

## THE NUMBER IS PUBLISHED, THE FLAG IS NOT

No `stale` key here either, and for 07-01's recorded reason: a flag computed at write time carries
`stale: false` for exactly the interval during which the row becomes stale — `pacing.py:196-199`'s
trap in mirror image. What goes out is the raw fact, and each consumer subtracts against its own
`now`. That is `status.py:119-133`'s own rule — *"the raw facts go out alongside any derived flag,
because a single value cannot tell a reader WHY"* — applied a fourth time, and it is why this plan
publishes a cadence rather than a verdict.

**Per retailer, in the existing `retailers` array, not on every watch row.** A cadence is a
per-retailer fact; a copy on each of fourteen watch rows is thirteen extra copies that can drift.
The consumer-side join is confirmed reachable rather than assumed: `served/boty/index.html:138`
already holds `d.retailers` and line 156 already interpolates `w.retailer`, so 07-05 can join them
with a lookup and no new payload shape.

**The key is `current_interval_seconds`,** and the name is a decision. Not `interval_seconds`: that
is already the operator's own **standing** key in `config/products.yaml`, and publishing a different
number under the same name on a served page is precisely the kind of quiet drift this phase exists
to remove. `current_` says which of the two intervals it is; `_seconds` states the unit on
`duration_seconds`' precedent.

## Scope fence

The missing rows — measured today at **3 rows for 14 configured watches** — are **07-04's**. The
three renderings, `cli._age_tag` and the dashboard's tag, are **07-05's**. **Nothing in this plan
compares a stamp to anything, computes a `stale` flag, renders a tag, or reads `read_at` at all.**
`boty/models.py`, `boty/retailers.py`, `boty/monitor.py` and `served/boty/index.html` are **not
touched**.

**And nothing in this plan changes when anything is fetched.** The backoff, its multiplier, the cap
and the politeness cadence are correct and are not this phase's subject. This plan exposes a number
that is currently thrown away; it does not alter the schedule that number describes. That is a claim
with a test behind it — Task 1's schedule-characterisation test asserts `due_at` for 0-8 consecutive
refusals at both configured intervals against **literal expected seconds**, not against the new
accessor, so a test that passed by re-deriving the answer through the code it is checking is not
available.

7. **`pacer-state.json` is written with a plain `write_text`, not atomically**, and this plan gives

   real one — over-reporting staleness rather than under-reporting it, which is the direction REQ-21
   prefers. It self-heals on the next check. The write is deliberately **not** changed to
   temp-and-replace here: that is the daemon's persistence path, this plan's rule is that pacing
   behaviour does not move, and the benefit accrues only to the second reader. Priced in the code
   (Task 2), carried as T-07-03b below.
