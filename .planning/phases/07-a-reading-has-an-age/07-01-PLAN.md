<objective>
Make the moment a reading was taken exist, and be correct, at the source.

`Result` gains `read_at: float | None`. Every one of the **20** `Result(` construction sites in
`boty/retailers.py` states it. `status.write` publishes it per watch row as `null` when absent.
One mutation pins the direction that matters most.

**Purpose.** REQ-21's opening measurement: asked when the Amazon and Walmart GO Plus + watches
last read `out_of_stock`, this system had no answer. Amazon's was reconstructible only from
refusal history; **Walmart's could not be established at all**, because a restart zeroed the
counter that held the evidence. Nothing records when a reading happened, so a row read four
seconds ago and one last read two days ago are byte-identical in shape. This plan creates the
datum that ends that. It does not render it, does not persist it, and does not compare it against
anything — 07-02 … 07-05 do those, and this plan's scope fence is stated in § *Scope fence* below.

**Output.** `Result.read_at`; 20 stated construction sites; one new `status.json` key; one new
mutation, watched going red; a static gate that cannot be satisfied by covering nineteen arms.

## The five criteria this phase is judged on (verbatim from ROADMAP.md, unedited)

  1. Every `Result` records when it was read, and that time is published per watch in `status.json`
  2. A reading with no recorded time is shown as UNKNOWN age, never as current — watched going red
  3. A reading older than its retailer's current interval is presented as stale in `status.json`, `boty check` and the dashboard, and the staleness is derived from the retailer's own pacing rather than a fixed clock
  4. The age survives a service restart, so a restart cannot make a two-day-old reading look fresh
  5. `make verify-offline` exits 0, and every gate this phase adds has been watched going red

**This plan owns criterion 1 whole, and the DATUM half of criterion 2** — an absent stamp is
`None`, never `now`. Criterion 2's *rendering* half is 07-05's. Criterion 5 binds here as the
red-watch on M31.

## THE TRAP, and it is this phase's own defect rebuilt if it is got wrong

`store=None` and `shipping=None` are stated on error arms because **nothing was read**. A refusal
does have a wall-clock moment — but it **took no reading**. Stamping it refreshes the age of a
reading that never happened, which is the 2026-08-12 Walmart failure rebuilt inside the fix meant
to prevent it. `pacing.py:196-199` wrote the lesson down already, for `_warned_since`:

> *"stamping at write time would refresh the record forever and the age-out would never fire once
> — a bound that cannot bind is worse than no bound, because it reads like one in the file."*

**So the stamp INVERTS the `store`/`shipping` rule, and the inversion is stated per arm rather
than inherited from a default.**

## AND THE NAIVE RULE IS WRONG AT TWO OF TWENTY SITES

*"An `except` arm read nothing"* is **measured false** at `check_bestbuy_api`'s `bad api json`
(`except ValueError`, raised by `page.json` — `get()` already returned, so bytes came back) and at
`sku not found` (an empty `products` list — Best Buy answered). Mis-stamping those two errs in the
**dangerous direction**: it marks a reading that *did* happen as having no age, and Best Buy is
then permanently UNKNOWN-aged on the one retailer this project reaches through an official API.

There is **no existing field that answers "was a page read"**. `availability is UNKNOWN` is not
that predicate — a store-gap UNKNOWN and a parse-failure UNKNOWN both read a page. `refused` is
closer and still not identical — `bad api json` sets no `refused` and still received a response.
`read_at` becoming that field is the honest framing, and Task 1 says so in the declaration.

## Scope fence

Persistence across a restart is **07-02's**. The retailer's current interval is **07-03's**. The
missing-row problem — measured today at **3 rows for 14 configured watches** — is **07-04's**.
Rendering in `boty check` and the dashboard is **07-05's**. Nothing in this plan compares a stamp
to anything, computes a `stale` flag, or reads `now`. `boty/cli.py`, `boty/monitor.py`,
`boty/pacing.py` and `served/boty/index.html` are **not touched**.

**No `stale` key is published, and that is a decision, not an omission.** A flag computed at write
time fails the mirror way to `pacing.py:196-199`: a row written fresh carries `stale: false` and
keeps carrying it for exactly the interval during which it becomes stale. The raw fact goes out
and every consumer subtracts against its own `now` — which is `status.py:119-133`'s own recorded
rule, *"the raw facts go out alongside any derived flag, because a single value cannot tell a
reader WHY"*, applied a third time.
