<objective>
`.github/workflows/` holds two files. Sixty-seven tests guard them, and **every rule the criterion
names is keyed to a filename** — `CI = WORKFLOWS / "ci.yml"`, then the same four rules written out
again for `RELEASE`. So a *third* workflow file — the one somebody adds next month — is guarded by
nothing, and the suite stays green while it happens.

That is not a forecast. It was measured against this tree today: a third workflow carrying a floating
action tag, a swallowed exit code, no `timeout-minutes` and `runs-on: ubuntu-latest` was written into
the real directory and `pytest tests/` returned **exit 0, 667 passed**.

Purpose: criterion 3 of five, and the highest-severity item in the phase. A workflow file is the only
artifact here that runs on somebody else's computer holding this repository's token. An unpinned
action in one is another party's mutable pointer executing under that token — the `tj-actions` shape
this repo's own comments already cite.

Output: four rule families re-keyed from a filename to the **directory**, each a pure function of
`dict[str, str]` returning findings prefixed with the filename; the per-file tests kept untouched as
the specific cases; a permanent in-suite red-watch on a synthetic third file; and the criterion
executed literally — the same non-compliant file, on disk, in the real directory, observed turning
the real suite **red**, then removed, with its removal enforced by a test from then on.

<decision>

## The rules are re-keyed to the directory. Not one rule's judgement changes

This is the whole design, and it is deliberately conservative: the four families are already correct
(F1). The defect is what they are *handed*. So three of four rule functions are **wrapped, not
rewritten**, and the wrapper's only work is iteration and a filename prefix.

The one exception is *timeout*, which has no function because it was never extracted. Extracting it is
the minimum act that lets it be handed a directory, and the extraction is **strengthening-only**:
identical bound (`isinstance(t, int) and 0 < t <= 30`), applied to every job.

## A registry, keyed by the criterion's own four words

`DIRECTORY_RULES` maps `"pin"`, `"exit-code"`, `"timeout"`, `"runner"` — verbatim from criterion 3 —
to the four functions, and a test pins the key set. That binds the criterion's sentence to the code
rather than leaving four rules to be counted by eye, and it makes a fifth family a one-line addition
instead of a fifth thing to remember. It is a **pin, not a rule**, in `TRUSTED_ACTION_OWNERS`' and
`UNREAD_POSITIONS`' sense: enumerated with the criterion quoted inline, so widening it means editing a
red test.

## Per-file tests stay. All 67 of them

They encode real, dated decisions — `pull_request` with no branch or path filter, `push` restricted to
`main`, the identity-check stage, the SHA pins, the environment string, the two-job split. The
directory rules are added **beside** them, never in place of them, and that is gated rather than
promised: a `<verify>` command compares this file's `test_*` names against `HEAD` and fails if any
name disappeared. Two test bodies are rewritten to call the extracted `_bad_timeouts` — same names,
same docstrings, same bound, strictly more coverage for `ci.yml` (all jobs rather than the first).
Nothing else is touched.

## Watched going red, three ways, and the third is the criterion itself

1. **Synthetic, permanent.** `NONCOMPLIANT_WORKFLOW` in `PUBLISH_WORKFLOW`'s established idiom, fed as
   `{RED_WATCH_NAME: ...}` beside the real texts, one violation per family, each asserted reported
   **with its filename** — and the clean side asserted in the same test, so the rule is not merely
   noisy.
2. **Synthetic, structural.** Every file made non-compliant at once, asserting each rule reports
   *every* file. A rule that `return`ed on the first finding would pass test 1 and leave the second
   file uncovered.
3. **On disk, once, observed.** The identical text written into the real
   `.github/workflows/`, the real suite run, the real red observed and its output recorded, the file
   removed in a `finally`. **The same command was already run on this tree and returned exit 0, 667
   passed (F1).** Green before, red after, same file, same command.

**And the removal becomes a gate rather than a habit:** a permanent test asserts `RED_WATCH_NAME` is
not in the directory. Forget to delete it and `make verify-offline` fails naming exactly that file.

## The on-disk probe never names a third-party action

`NONCOMPLIANT_WORKFLOW` uses `actions/checkout@v4` — an owner already in `TRUSTED_ACTION_OWNERS`, at a
floating tag. The violation is the *mutable ref*, which is what the rule catches. Writing
`some-vendor/...@<sha>` into the tree, even for ten seconds, would be typing the `tj-actions` shape
into a public repository to test a rule about the `tj-actions` shape. The untrusted-owner half is
watched **in-suite only**, on a variant derived with `.replace()` from the same constant, in this
file's established derive-don't-retype idiom.

## An unreadable workflow raises. It is not reported clean

A file `yaml.safe_load` returns anything but a mapping for — empty, a bare scalar, a list — must not
pass through a rule as "no findings". `NoTriggerBlock`'s docstring already settles this for the
trigger rule: *"a rule that reports 'no triggers' for a file it could not read passes by not
running."* Add `UnreadableWorkflow` beside it, in the same voice, raised by a shared `_parsed(name,
text)` helper, and watch it raise. **A file this gate cannot read is not a file it has checked.**
