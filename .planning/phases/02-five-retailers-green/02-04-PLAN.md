<objective>
Add Pokémon Center and the Nintendo store, and clear the MVP bar: five retailers
reporting trustworthy stock, every one control-verified.

`02-PATTERNS.md` §1 is emphatic that **these two probably need no new checker at
all**. There is no adapter class and no registry in this codebase: a retailer is a
string key on `Watch.retailer` straight out of YAML, an entry in `FIRST_PARTY`
(and `MARKETPLACES` only if the site has a marketplace), and optionally a branch
in `_make_checker`. If these pages carry schema.org `Product` markup, the existing
`check_html` path already handles them. So task 1 is a cheap probe, not an adapter
build — do not budget a full adapter for what may be a two-line allow-list change.

Purpose: REQ-05 and REQ-06, phase criteria 2, 3, 4, 5, 6 and 7. Pokémon Center is
first-party for Pokémon goods and plausibly the single most likely genuine restock
source for a GO Plus +; Nintendo's store is first-party for the hardware itself.

D-03 governs the failure case for each independently: a retailer that cannot be
reached is documented with evidence, never faked. Walk the escalation ladder in
order — rung 1 (`curl_cffi`), rung 2 (an official/structured API, but only if a
fresh clone can obtain the credential), rung 3 (the browser transport 02-01 built,
flagged DEGRADED), rung 4 (drop, with evidence). Stop at the first rung that works
and record which one it was.

Output: two registered retailers with control products, fixture-backed offline
tests, a completed support matrix, and a green end-to-end run.
</objective>

<design>
**Registering a retailer, in full.** Three things, no more:
1. `retailer: pokemoncenter` on a watch in `config/products.yaml`
   (`boty/config.py:113-120` does `retailer=entry["retailer"]` with no validation
   and no enum — the YAML entry *is* the registration).
2. An entry in `FIRST_PARTY` (`boty/retailers.py:25-30`). Both of these sites are
   single-seller: put them in `FIRST_PARTY` and leave them **out** of
   `MARKETPLACES`, so `_pick`'s unattributed-offer fallback covers pages with no
   seller node — the GameStop shape.
3. A `_make_checker` branch only if they need something other than `check_html`.

**The test that must move.** `tests/test_retailers.py:203`
(`test_retailer_with_no_first_party_list_is_unknown_not_out_of_stock`) uses
`pokemoncenter` as its example of an unconfigured retailer. The moment
`FIRST_PARTY["pokemoncenter"]` exists, that test stops exercising WR-03 — the
guarantee that a config gap yields UNKNOWN rather than a confident OUT_OF_STOCK.
Repoint it at a key that is genuinely not configured (`costco` is a reasonable
choice: named in the roadmap's narrowing rationale as deliberately out of scope)
and keep every assertion, including `is not Availability.OUT_OF_STOCK`. Do not
delete it; the WR-03 door is exactly the door three Phase 2 adapters arrive
through.

**If a new extractor is needed.** Pokémon Center is a Salesforce/Next-ish SPA and
the Nintendo store is a Next.js app, so either could carry a `__NEXT_DATA__`
payload at a *different* path from Walmart's. If so, do **not** generalise
`nextdata_offers` into a searcher — the explicit `_WALMART_PRODUCT_PATH` constant
exists because a product page also embeds recommendations, bundles and "customers
also bought", each with its own `availabilityStatus`, and a generic walk happily
reports a $12 screen protector as your restock. Add a second named path constant
and a second function, or parameterise the path. Whatever you add returns
`list[Offer] | None` with the three-valued contract intact, and gets its own
`source` label threaded into `Result.detail` via the existing `if not offers:`
chain in the verdict path.

**Controls.** `scripts/control_check.py:139-150` computes `configured - verified`
before making any request and exits 2 with the list, so adding either retailer
without a control breaks `make verify` by design (WR-04, D-02). Both controls land
in this plan, in the same commit as their retailer. Selection rule from
`config/products.yaml:49-51`: first-party, restocked routinely, never a
marketplace buy-box fight. For Pokémon Center and Nintendo pick an evergreen
first-party staple — a perennial plush, a standing accessory, a first-party
peripheral that never sells out. Do not use a scarce console or a limited drop.
Name each `CONTROL — <product>`, `control: true`, **no `max_price`**.

**The five-retailer count.** After this plan `config/products.yaml` should carry
gamestop, walmart, bestbuy, pokemoncenter and nintendo. If Best Buy landed on
Branch B in 02-03, or if either retailer here lands on rung 4, the count falls
short of criterion 4 — surface that, do not paper over it.

**Test set each new adapter owes**, mirroring what GameStop and Walmart have
(`02-PATTERNS.md` §4): product page reads the expected availability and price;
control page reads IN_STOCK and is alertable; unparseable page is UNKNOWN and
explicitly `is not Availability.OUT_OF_STOCK`; `Blocked` is UNKNOWN with "blocked"
in the detail; `FetchError` is UNKNOWN with "fetch failed" in the detail. Plus
extractor-level tests in `tests/test_parse.py` if a new extractor was added:
`None` on no blob, `None` on malformed JSON, `None` on a missing product node,
`""` gives `None`.
</design>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pokemoncenter.com / nintendo.com HTML → parser → verdict | Attacker-controlled markup decides a stock claim and a push notification |
| new `FIRST_PARTY` entries → `_pick` | The allow-list is the only thing standing between a reseller listing and an alert |
| `config/products.yaml` → `control_check.py` | The gate that judges every detector is driven by the same file the monitor reads |
| verdicts → `served/boty/status.json` → HTTP | Retailer-derived `detail` and `url` are published verbatim |
