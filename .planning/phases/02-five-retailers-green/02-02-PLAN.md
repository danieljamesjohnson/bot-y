<objective>
Give a reading a *provenance*. Today `boty/models.py` has no concept of reading
quality, method or rung — `02-PATTERNS.md` §6 is blunt that this is new design,
not pattern-following, and names the exact ways a naive implementation breaks the
codebase.

This plan adds that concept once, as shared infrastructure, so the three adapter
plans consume it instead of each inventing it. It also closes deferred finding
IN-03, because Pokémon Center and Nintendo are precisely the first-party sites
likely to emit a compound `@type` and 02-04 must not spend a task diagnosing a
mystery UNKNOWN that `01-REVIEW.md` already solved verbatim.

Purpose: D-01 requires Best Buy to be flagged DEGRADED on the browser path and
un-flagged on the API path, and phase criterion 6 requires the support matrix to
record which escalation rung each retailer landed on. Both need a single field
that says how a reading was obtained. D-03 needs it too: "documented, not faked"
is only meaningful if the *published* status distinguishes a confident reading
from a lower-confidence one.

Output: a `Rung` enum, `Result.rung` and `Result.degraded`, both surfaced in
`status.json` and `boty check`, a mutation proving the flag is load-bearing, and
the IN-03 parser fix.

**Locked decisions honoured:** D-01 (DEGRADED on browser, dropped on API);
D-03 (a lower-confidence reading is labelled as such, in the matrix and in
`boty check` output).
</objective>

<design>
The design question `02-PATTERNS.md` §6 hands to the planner is answered here.
Build exactly this; do not re-derive it.

**Degradation is a property of the reading method, which is only known inside the
checker. So it lives on `Result`, not on `Watch` and not on `Health`.**

In `boty/models.py`, add a second enum next to `Availability`:

- `class Rung(str, Enum)` with members `TLS = "tls"`, `API = "api"`,
  `BROWSER = "browser"` — one per rung of the escalation ladder in
  `.planning/ROADMAP.md`. Rung 4 (dropped) has no member on purpose: a dropped
  retailer produces no readings at all, so a `Rung` for it would be a value that
  can never appear in a `Result`. Docstring must say that.
- On `Result`, a new field `rung: Rung = Rung.TLS` declared **last**, after `url`.
  A default on a frozen dataclass keeps every existing construction site valid —
  `boty/retailers.py` builds `Result` positionally for `watch`/`availability` and
  by keyword thereafter — so this is a low-blast-radius change and must stay one.
- On `Result`, a derived property `degraded -> bool` returning
  `self.rung is Rung.BROWSER`. Derived rather than stored so there is one source
  of truth: the matrix's "which rung" and the DEGRADED flag cannot disagree.

Three things this must NOT do, each of which breaks something concrete:

1. **`Rung` is not a fourth `Availability` member.** Adding it there breaks
   `assess_health` (`boty/monitor.py:78`, `is not Availability.IN_STOCK`),
   `transitioned_to_stock` (`boty/monitor.py:53-58`), and `cli.SYMBOL`
   (`boty/cli.py:26-30`), which is a dict indexed unconditionally at `:46` — a
   missing key is a `KeyError` mid-report. Degradation is orthogonal to what the
   stock reading says.
2. **A degraded reading must NOT make `Health.ok` False.** `assess_health` answers
   "has this detector been verified by a control", not "how confident is the
   transport". If degradation flipped health, Best Buy would raise a permanent
   health warning and phase success criterion 4 — "`boty check` reports five or
   more retailers with **no health warnings**" — could never be met. Leave
   `boty/monitor.py` untouched, and say why in a comment where a future reader
   would otherwise be tempted.
3. **Do not touch `Result.alertable`.** A degraded reading is still a real
   reading; suppressing alerts on it would defeat the point of supporting the
   retailer at all.

**Surfacing.** Two places, both mechanical:

- `boty/status.py:34-46` — the per-watch dict is a flat literal. Add
  `"rung": r.rung.value` and `"degraded": r.degraded`. This is what the dashboard
  and the support matrix read.
- `boty/cli.py:42-52` — `_report` already computes
  `tag = " [control]" if r.watch.control else ""`. Compose instead: build a list
  of tags, append `"[control]"` when the watch is a control and `"[degraded]"`
  when `r.degraded`, and join. Keep the line width behaviour sane. `SYMBOL`
  itself must not gain a key and must not be indexed with anything new.

**Mutation M6.** `scripts/mutation_check.py` M4/M5 exist because the gate could
not see the layer where the worst bug lived. If DEGRADED is load-bearing for
trust, clearing it must turn the suite red. Add a sixth `Mutation` with
`ident="M6"`, `target="boty/models.py"`, `search` set to the exact source
substring of the degraded property's return statement, `replace` returning
`False`, and a `breaks` string saying that a browser-read verdict would then be
published as if it were a first-class TLS reading. `apply_mutation` raises if the
anchor is not found or the substitution is a no-op, so the `search` string must
match the file byte for byte including indentation.

**IN-03.** `boty/parse.py:71` is `if node.get("@type") != "Product": continue`,
which misses `"@type": ["Product", "ProductModel"]`. `01-REVIEW.md:718-733`
supplies the fix verbatim: read `@type`, wrap a non-list in a list, and `continue`
unless `"Product"` is in it. Note the `None` case still works — a node with no
`@type` becomes `[None]`, which does not contain `"Product"`, so `saw_product`
stays False and the extractor still returns `None` rather than `[]`. That
distinction is the one `tests/test_parse.py` exists to protect.
</design>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| retailer JSON-LD → `ldjson_offers` | Attacker-controlled JSON of arbitrary shape is walked and coerced |
| Result fields → `served/boty/status.json` → HTTP | Everything on a Result is published verbatim to a file served through the Mission Control proxy |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-07 | Spoofing | A low-confidence browser reading presented as a first-class one | mitigate | `Result.rung` is set by the checker that actually did the work and is derived — not stored — into `degraded`, so the matrix claim and the runtime flag cannot drift apart. M6 makes silently clearing it a red suite. |
| T-02-08 | Information Disclosure | New `rung` / `degraded` keys in the served `status.json` | accept | Both are enum-constrained values computed from our own code paths; neither is retailer-controlled and neither can carry a credential. `detail` and `url` remain the fields with a redaction obligation (handled in 02-03). |
| T-02-09 | Tampering | Malformed `@type` (dict, nested list, non-string) crashing the extractor | mitigate | The IN-03 fix wraps a non-list in a list and tests membership; no attribute access on the value, so a dict or int simply fails the membership test and the node is skipped. A `json.JSONDecodeError` in any single block is already skipped by `continue` (`boty/parse.py:68-69`). |
| T-02-10 | Denial of Service | Adding a required field to a frozen dataclass breaking every construction site | mitigate | `rung` is declared last with a default; task 1's `<verify>` runs the entire pre-existing suite unchanged as the proof. |
| T-02-SC | Tampering | package-manager installs | n/a | This plan installs nothing. No new dependency is added. |
</threat_model>
