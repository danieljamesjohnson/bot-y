<objective>
This repo is public, declares `license = { text = "MIT" }` in `pyproject.toml:11`,
has a `## License` heading in `README.md:411-413` saying MIT — and ships no
licence text at all. `git ls-files | grep -ci licen` returns `0`. The GitHub API
reports `license: None`. A public project asserting a licence with no licence
text arguably grants nobody any rights.

That is not a missing file. It is the exact failure shape
`tests/test_support_matrix.py` was written about: a contract asserted at the
producing end and quietly unimplemented at the consuming one. So the fix carries
a gate, and the gate is the point.

Purpose: close the blocking half of Phase 4 criterion 3 (`pip install bot-y`
works) by making the licence real, making the packaging metadata say so in the
form modern setuptools actually wants, deciding what a published sdist ships,
and putting a test in `make verify` that goes red the moment the declaration and
the file disagree.

Output: `LICENSE`, `MANIFEST.in`, a surgically-edited `pyproject.toml`, and
`tests/test_packaging_metadata.py`.

**Version stays at `0.1.0`.** The bump to 1.0.0 belongs with the release in
04-05 and must not happen here.

**This plan moved from wave 1 to wave 2 and now depends on 04-01.** Both plans need
entries added to `SANDBOX_CONTENTS` in `scripts/mutation_check.py`, which made that
file contested inside a single wave. Consolidating the four entries into one edit is
not available — `build_sandbox()` raises `HarnessError` for any entry with no file
behind it, so whichever plan made the single edit would name files the other plan had
not created yet and would redden its own `make verify-offline`. **Each entry lands in
the same commit as the file it names.** 04-01 adds `CONTRIBUTING.md` and `hooks` in
wave 1; this plan adds `LICENSE` and `MANIFEST.in`, and makes the sandbox a git tree,
in wave 2. **The `hooks` entry is a hard dependency, not just an ordering

`hooks/pre-commit` exists inside the sandbox and fails without 04-01's entry
(measured fact 9a). The cost is wave 1's parallelism, accepted on the grounds that an
unattributable red `make verify` is worse than a serial wave on a solo project.

Established first-hand during planning, on this box, against setuptools 83.0.0
(the version `pip`'s build isolation resolves today for `setuptools>=68`). Do
not re-derive these; do check them still hold if a command behaves oddly.

1. **`license = { text = "MIT" }` is deprecated and dated.** Preparing wheel
   metadata with the current `pyproject.toml` prints:
   `SetuptoolsDeprecationWarning: `project.license` as a TOML table is deprecated`
   … *"Please use a simple string containing a SPDX expression for
   `project.license`. You can also use `project.license-files`. (Both options
   available on setuptools>=77.0.0). By 2027-Feb-18, you need to update your
   project and remove deprecated calls or your builds will no longer be
   supported."* It still builds, and emits `Metadata-Version: 2.4` with a
   free-text `License: MIT` field.

2. **The PEP 639 form is clean.** `license = "MIT"` plus
   `license-files = ["LICENSE"]` emits `License-Expression: MIT` and
   `License-File: LICENSE`, places the file at
   `bot_y-0.1.0.dist-info/licenses/LICENSE`, and prints no warning at all.

3. **A `License ::` classifier alongside the SPDX expression is a hard build
   error**, not a warning:
   `setuptools.errors.InvalidConfigError: License classifiers have been
   superseded by license expressions (see PEP 639). Please remove: License ::
   OSI Approved :: MIT License`. So the classifier list must not contain one.

4. **setuptools does NOT enforce that a `license-files` target exists.** With
   `license-files = ["LICENSE"]` and no `LICENSE` on disk, the build succeeds
   silently, emits `License-Expression: MIT`, emits **no** `License-File`, and
   writes no `licenses/` directory. *The build is not the gate.* This is the
   single most important fact in this plan and it is why task 3 exists.

5. **`[tool.setuptools.packages.find] include = ["boty*"]` constrains the WHEEL,
   not the sdist.** Built from the tracked tree with no `MANIFEST.in`, the sdist
   contained `boty/*.py`, `README.md`, `pyproject.toml`, `PKG-INFO`, a generated
   `setup.cfg`, `bot_y.egg-info/*` — **and every `tests/test_*.py`**, while
   shipping neither `tests/conftest.py`, `tests/fixtures/`, `config/products.yaml`
   nor `scripts/`. That is a test suite that cannot run, published to PyPI.

6. **`prune` is silent, `exclude` is noisy.** `prune tests` removed `tests/`
   from the sdist. `prune` lines naming directories that were never included
   printed nothing. An `exclude` line naming a file that was never included
   printed `warning: no previously-included files found matching '…'` on every
   build. Use `prune`; do not add `exclude` lines for files that never enter.

7. **`tomllib` is Python 3.11+.** `requires-python = ">=3.10"` and
   `[tool.mypy] python_version = "3.10"` both claim 3.10, and 04-04 pins CI to
   3.10 precisely because testing the floor is what the config claims. So the
   test module in task 3 must not import `tomllib`. Acceptance commands run
   through `.venv/bin/python` (3.12 on this box) and may use it freely.

8. **The mutation sandbox copies a fixed tuple and is not a git repository.**
   `scripts/mutation_check.py` `build_sandbox()` copies only the entries in
   `SANDBOX_CONTENTS` into a temp directory; `run_suite()` runs `pytest tests -q`
   with `cwd` set there; `run_baseline()` requires that unmutated run to exit 0
   and raises `HarnessError` otherwise, which kills `make verify` and
   `make verify-offline`. At `b0a272f` the tuple was `("boty", "tests",
   "scripts", "config", "served", "docs", "pyproject.toml", "Makefile",
   "README.md")`; 04-01 added `"CONTRIBUTING.md"` and `"hooks"` in wave 1.

   relative to its own parent, so both must be added; and `git ls-files` inside
   that directory exits **128** with `fatal: not a git repository`, because
   nothing ever runs `git init` there.

9b. **`git init -q -c init.defaultBranch=main` is invalid git syntax.** Measured
    on this box (git 2.43.0): `git init -q -c init.defaultBranch=main .` prints
    ``error: unknown switch `c` `` followed by the usage block, and exits **129**.
    `-c` is a top-level git option, not an `init` subcommand option. The correct
    invocation is `git -c init.defaultBranch=main init -q`, measured to exit 0,
    print nothing at all, and leave `HEAD` at `refs/heads/main`. Write it that way
    — the wrong order makes `build_sandbox()` raise on every single call, and the
    `HarnessError` it produces points the reader at `SANDBOX_CONTENTS`, which is
    not the cause.

9c. **`git add -A` stages one file the real repo deliberately never tracks.**
    Measured: the sandbox index carries 65 files (66 once `hooks` is in the
    tuple), and differencing that set against the real repo's `git ls-files`
    leaves exactly one entry — `served/boty/status.json`. It is `.gitignore`d in
    the real repo, but `.gitignore` is not in `SANDBOX_CONTENTS`, so git inside
    the sandbox has never heard of it; and
    `_IGNORE = ignore_patterns("__pycache__", "*.pyc", ".pytest_cache",
    "*.egg-info")` does not match it, so the copy loop brings it in.

    It is the **only** untracked-but-copied file — measured by set difference,
    not assumed. That matters because with the index in place the newly un-skipped
    `test_the_repo_is_clean_right_now` runs the identity scan over it *inside the
    sandbox*. Today that scan is clean (measured: `scan([status.json], root)` →
    `[]`). But the file is a runtime artifact rewritten by every live
    `make verify`; it currently holds 11 `url` fields and a `reason` reading
    `backing off after 3 refusal(s) — next attempt in ~224 min`, and `reason` is
    populated from retailer-failure exception text — exactly the string class that
    can pick up a local path or a host. So a future `make verify` would die as a
    `HarnessError` caused by a file that is in neither the repository nor the
    diff, while this plan's own text forbids the obvious fix.

    Nothing reads the sandbox's copy: every test that touches `status.json` writes
    to `tmp_path` (`tests/test_pacing.py:285`, `tests/test_cli_watch.py:44`, `:316`,
    `:358`, `tests/test_status.py:56`). The file has no business in the sandbox at
    all. Task 3 adds `"status.json"` to `_IGNORE`.

9d. **The git index makes the mutation gate materially slower, and that is
    accepted.** Measured over four runs, two per case: the sandbox suite goes from
    **5.5 s** to **8.9 s**. `git init` plus `git add -A` together cost **0.08 s** —
    negligible; the whole delta is the un-skipped identity scan walking every
    tracked file in the sandbox. `main()` builds nine sandboxes (`run_baseline`
    plus one per each of the eight `MUTATIONS`), so `make verify`'s `mutation`
    stage gains roughly **+3.3 s × 9 ≈ 30 seconds** — on every run, on every
    contributor's machine, and inside 04-04's CI job. A real strengthening at a
    real price, not a defect. It goes in the summary so that 04-04 or a
    contributor does not later diagnose it as unexplained CI slowness and "fix" it
    by removing the index.

9e. **`module_from_spec` + `exec_module` alone cannot import
    `scripts/mutation_check.py`.** Measured: the obvious one-liner
    `s = spec_from_file_location("mc", …); m = module_from_spec(s);
    s.loader.exec_module(m)` dies with
    `AttributeError: 'NoneType' object has no attribute '__dict__'` raised from
    `dataclasses._is_type`, because `@dataclass(frozen=True)` on `Mutation`
    resolves annotations through `sys.modules.get(cls.__module__)` and
    `module_from_spec` does not register the module there. Every command in this
    plan that imports the harness by path therefore sets `sys.modules["mc"] = m`
    **before** `exec_module`. Without it the check fails for a reason that has
    nothing to do with what it is checking. *(04-01, 04-03 and 04-04 carried the
    same one-liner. All three were fixed on 2026-08-04, each with a comment naming
    the dataclass cause — so this is a closed issue, not an errand. If you find a
    NEW unregistered `spec_from_file_location(…, "scripts/mutation_check.py")`
    anywhere, it has the same defect and the same one-word fix.)*

10. **Tracked top-level entries today**, from `git ls-files`: directories
    `boty/`, `config/`, `deploy/`, `docs/`, `hooks/`, `.planning/`, `scripts/`,
    `served/`, `tests/`; files `.gitignore`, `Makefile`, `pyproject.toml`,

    satisfiable there rather than merely runnable.

11. **`git ls-files` has two distinct failure shapes and only one is an error
    code.** Outside a repository it exits 128 with `fatal: not a git repository`.
    Inside a repository with an empty index it exits **0** and prints nothing.
    A rule that only checks the exit code treats the second as "no tracked
    directories" and reports success. Both must be caught.
