<objective>
This is the plan that hands the project to its maintainer, and then measures what
he did.

Four plans in this phase produced things that can be read: documentation, a
licence, a linter, a workflow, a proof script. 04-05 went one better and
*measured* a wheel — built it, installed it into a clean venv, ran the console
script, and found a real packaging bug doing it. But there is exactly one claim in
Phase 4 that cannot be established from this machine at all: **that `pip install
bot-y` works from PyPI.** Nothing local can prove it, because the thing being
tested is a download, and the download does not exist until somebody with Dan's
credentials publishes it.

So this plan does three things and nothing else. It assembles the handoff **from
the shipped tree rather than from a plan** — the environment string read out of
the workflow file that actually landed, the version read out of the
`pyproject.toml` that actually landed, the push state read off `origin`. It stops,
and asks Dan to do the four things only he can do. Then it measures whatever he
produced and writes down the five verdicts, each with the command that produced it
or the reason it could not be produced.

Purpose: REQ-11, and Phase 4 criteria 3 and 5 — closed by Dan, not by an agent.

Output: `.planning/phases/04-open-source-ready/04-06-HANDOFF.md`, a five-row
outcome table in `.planning/ROADMAP.md`, and a summary that is a record rather
than a report.

**This plan changes no source file.** Not one line of `boty/`, `tests/`,
`scripts/`, `Makefile`, `README.md`, `pyproject.toml` or `.github/`. That is a
property worth stating rather than a coincidence: it is what makes this plan
**safe to sit unexecuted indefinitely**. Waves 1-4 complete without it, nothing in
them waits on it, and if Dan never runs it the tree is exactly the tree 04-05
left — one that builds, installs, lints, types, tests and CIs, and simply has not
been published.

**Three tasks, not two, and the middle one is a wall.** Task 1 is automated
pre-flight. Task 2 is the checkpoint. Task 3 measures and records. The context
cost is low by construction — this plan writes no code, so its tasks are command
invocations and their transcripts — which is why three fits where three normally
would not.
</objective>

<constraints>

**The agent publishes nothing, pushes nothing, tags nothing, and configures
nothing authenticated.** Forbidden in every task of this plan, in any form,
including inside a script the plan writes:

`git push` · `git tag` · `twine upload` · `python -m twine upload` ·
`gh release create` · `gh release edit` · `gh workflow run` · `gh secret set` ·
`gh api` with `-X POST`/`PATCH`/`PUT`/`DELETE` · `gh repo edit` · any curl with
`-X POST` against pypi.org or api.github.com.

Measured fact 6 is why this is written as a list rather than as a principle: the
`gh` on this host holds `repo`, `workflow` and `write:packages`, so the executor
*can* do all of it. `04-CONTEXT.md` § *NOT at Claude's discretion* reserves both
criteria for Dan by name, and the two reasons are not symmetric — a first publish
**permanently claims the PyPI name**, and a pushed tag is **visible to anyone
watching the repository**. Neither is undoable by apologising.

**Read-only `gh` and read-only HTTP are allowed and expected**: `gh run list`,
`gh run view`, `gh api` with no `-X` (a GET), `git ls-remote`, `git fetch`, and
plain `curl` GETs against pypi.org and api.github.com. Watching a run is not
publishing it.

**Nothing in this plan is a prerequisite for anything in waves 1-4.** If it is
never executed, or executed and declined, the tree is unchanged and every other
plan in this phase stands. Any task that would make wave 1-4 work depend on a
publish is out of scope by construction.

**Every value Dan is asked to type is read out of the shipped tree at execution
time, not copied out of this plan.** The environment string comes from
`.github/workflows/release.yml` as it actually landed; the distribution name and
version come from `pyproject.toml` as it actually landed; the unpushed-commit
count comes from `origin`. Where this plan states an expected value — `pypi`,
`release.yml`, `1.0.0`, `danieljamesjohnson/bot-y` — it states it as an
expectation to confirm. **If the tree and this plan disagree, the tree wins and
the disagreement goes in the summary.**

**The environment name is the coupling that bites, and it bites in the wrong
place.** PyPI's trusted-publisher form and the workflow's `environment:` key must
carry the **identical string**. A mismatch does not fail as "wrong environment" —
it fails at the OIDC exchange as an invalid or unknown publisher, which reads like
a problem with the workflow, the token, or the project name. 04-05 flagged this
for exactly this reason. State the string once, verbatim, and have Dan copy it.

**No success criterion is reworded.** Not to make it meetable, not to make it
clearer, not to fold two into one. Phase 3.1 recorded criterion 1 UNMET, was
offered a rewrite that would have made it achievable, and declined — "a criterion
that stands unmet with the reason written down is worth more than one quietly
moved." Criteria 3 and 5 standing UNMET is an **acceptable close** for this phase.
An acceptance criterion asserts the ROADMAP diff is additions only.

**Nothing is marked MET that was not measured.** A verdict cell contains a command
output, a count, a URL or a named reason. Not an adjective, and not a citation of
another plan's claim about itself. Criterion 4 in particular is recorded as
**preserved** — it was MET before Phase 4 opened, and the honest statement is that
this phase did not break it.

**The handoff card lives in `.planning/`, not in `docs/`.** A maintainer runbook
under `docs/` would be a second document inside the surface 04-01 gated with
`tests/test_contributor_docs.py`, and widening a wave-1 gate from wave 5 to
publish a document about a release that has not happened is the wrong order. It is
also the wrong *time*: a release runbook is worth writing once the first real
publish has been observed, so it records what happened rather than what was
expected. Recorded here so the omission reads as a decision.

</constraints>
