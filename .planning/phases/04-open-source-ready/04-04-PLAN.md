<objective>
There is no `.github/` directory in this repository. REQ-10 says CI runs lint, the type
check and the offline test suite on every PR; 04-03 landed the lint half and wired it into
`make verify`. This plan lands the other half, and it is the first time anything in this
repo runs anywhere but Dan's machine.

The whole design is one sentence: **CI delegates to the `Makefile` rather than re-listing
checks.** The Makefile header already says why — "`make verify` is the contract … it has
exactly one job: exit non-zero if ANY check fails" — and a workflow that re-lists pytest,
mypy and ruff as separate steps is a second definition of the order and of the verdict,
free to drift from the one a maintainer runs. So the job is one step: `make
verify-offline`. Never `make verify`, which makes live requests to six retailers and would
put them on GitHub's IP ranges at pull-request frequency, against this project's own
politeness budget.

Three things make this more than sixteen lines of YAML:

1. **A workflow on a public repo is the supply-chain foothold.** A `pull_request` trigger
   runs a fork's code. `pull_request_target` would run it with the base repository's write
   token and its secrets. A mutable action tag is somebody else's repository deciding what
   executes here. Each of those is decided deliberately below and then asserted by a test.

2. **No pull request can be run offline, so the proof is a gate, not a claim.**
   `tests/test_ci_workflow.py` reads the workflow the way `tests/test_support_matrix.py`
   reads the README — rules as functions over the text, the shipped file asserted against
   them, and the same functions run against deliberately broken copies. PyYAML is already
   a runtime dependency, so this adds nothing.

3. **The declared floor has never been executed.** `requires-python = ">=3.10"` and
   `[tool.mypy] python_version = "3.10"` have been claims since Phase 1, verified against
   nothing: this repo's `.venv` is Python 3.12.3 and no 3.10 exists on the box. CI on 3.10
   is the first exercise of that claim, and a contributor's first pull request is the worst
   possible place to discover it. Task 1 exercises it locally first, in a container, from a
   shallow clone — which is also how the `actions/checkout` question gets an answer instead
   of an argument.

Purpose: REQ-10's CI half and Phase 4 criterion 2 — CI runs the test suite on every PR,
offline, against fixtures.

Output: `.github/workflows/ci.yml`, `tests/test_ci_workflow.py`, and the two one-line
consequences of this repository acquiring a `.github/` directory at all.
</objective>

<constraints>

**`make verify-offline`, never `make verify`.** `verify` makes live requests to six
retailers. At pull-request frequency, from GitHub's IP ranges, that is exactly the trade
`docs/retailer-evidence.md` argues against and the pacing and backoff work in
`config/products.yaml` was built to avoid. `verify-offline` delegates to `verify` with
`CONTROL_FLAGS=--offline`, so `control_check.py` exits 3, the verdict reads `PASS (OFFLINE
— …)` and the exit code is 0. That verdict wording is honest and must not be reworded to
look unconditionally green.

**Nothing may flatten an exit code.** No `continue-on-error`, no `|| true`, no `; true`, no
`set +e`, no `exit 0` inside a run block, and no piping the make invocation through `tee` or
anything else — a pipeline takes the status of its last command, which is the failure mode
the Makefile header was written about and which is equally available in YAML.

**`.[dev]` and never `.[browser]`.** `nodriver` is AGPL-3.0 against this MIT project and its
optionality is a recorded maintainer decision dated 2026-08-02 in `pyproject.toml`. Its
absence needs no special handling here: under `--offline` the control check exits 3 before
the browser rung is ever reached.

**The workflow's own comments will contain the strings the rules forbid.** This file must
carry a decision-record comment block in this repo's idiom, and that block has to name
`pull_request_target`, `continue-on-error` and `make verify` in order to explain why they
are absent. A grep gate over the raw file would therefore match its own documentation and
pass forever. **Every forbidden-string rule — in the tests and in this plan's acceptance
commands — runs over a comment-stripped view of the file.** Rules that need a comment (the
action pin's trailing version) use the raw view, and the two views are named, separate
helpers with the reason written beside them.

**Line numbers cited here are from `b0a272f`, and three plans have landed since. Locate
everything by content.** `grep -n` for the anchor first; if it is not where this plan says,
trust the grep. This applies especially to `SANDBOX_CONTENTS`, to `MANIFEST.in`'s prune list
and to 04-02's helper names.

**Do not touch `README.md`, `pyproject.toml` or the `Makefile`.** 04-01 owns README prose,
04-03 owns the stage table, and both asserted their own diffs; `README.md` also carries the
support matrix, whose locator binds by header cells and which a stray seven-column table
would hijack. **No CI badge**: a badge asserts a status nobody has observed, which is the
asserted-but-unimplemented shape this entire phase exists to close. This plan adds no
dependency, so `pyproject.toml` is not opened either.

**A test that skips when its input is missing is forbidden.** If the workflow file is
absent, `tests/test_ci_workflow.py` must fail, not skip. `addopts = "-ra"` exists in this
repo because a test that quietly stops running is the failure mode it was configured to
surface, and the mutation sandbox is precisely where that would otherwise happen.

</constraints>

| CI logs → the public internet | Anything printed by any step is world-readable and effectively permanent. This repo has already leaked a real IP to `origin/main` once |
| `.github/workflows/` → repository privilege | `on:` and `permissions:` decide what a run may do. 04-05 is about to add a workflow that legitimately needs far more privilege than this one, into the same directory |
| CI → six third-party retailers | `make verify` reaches real stores. GitHub's IP ranges plus pull-request frequency is a different politeness question from one developer's laptop |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04-01 | Elevation of privilege | `on:` trigger selection | mitigate | `pull_request_target` is used by no workflow in this repository. It runs the base repo's workflow with a write-scoped token and repository secrets against author-controlled code, which is the standard exfiltration path for public repos. `_pr_triggered_privilege` enforces it across every file in `.github/workflows/`, not only `ci.yml`, and is watched failing against a synthetic workflow that uses it |
| T-04-04-02 | Elevation of privilege | `permissions:` | mitigate | Workflow-level `permissions: contents: read`; no job declares its own. Stated accurately in the file's comment: for a fork PR GitHub already forces the token read-only, so this is what protects the `push: main` run and any branch pushed inside this repository. `_write_grants` reports any `write` level and any `id-token` or `packages` scope at any level, workflow or job |
| T-04-04-03 | Tampering / supply chain | `uses: actions/...` | mitigate | Both actions are `actions/`-published and pinned to full 40-character commit SHAs with the version in a trailing comment. A mutable tag is another party's pointer: `tj-actions/changed-files` had its tags repointed at a malicious commit in March 2025 and thousands of public repositories printed secrets into their logs. The SHAs are resolved with `git ls-remote` at execution time and the resolution is recorded; the test asserts the *shape* (first-party owner, 40-hex ref, version comment) rather than a literal SHA, because a literal in the test would be a second definition free to drift from the workflow |
| T-04-04-04 | Tampering / injection | `${{ }}` inside a `run:` block | mitigate | No run block contains `${{`. A pull-request title or branch name interpolated into a shell is arbitrary code execution on the runner with the job's token. The one expression in the file is in `concurrency`, where GitHub evaluates it to a value; the rule is scoped to run blocks for exactly that reason, and the distinction is written down next to it |
| T-04-04-05 | Information disclosure | `scripts/identity_check.py` output in a public run log | **accept**, with limits | Measured: `_identity_leaks` prints the offending value — a real IP, a real postcode — and CI logs are public. Suppressing it is refused outright: a guard whose output is hidden is not a guard, and this repo's whole identity story is that the rule must be watchable. The risk is bounded by what CI can see: it runs against pushed commits, so any value it prints is already public in the repository or in the fork that pushed it — the log is a second copy of a disclosure that has already happened, not a new one. Concretely limited by: no `set -x`, no `env` dump, no context interpolation, and `identity` running first inside `verify` so a leak stops the run before anything else prints. The response to a red `identity` in CI is rotation and redaction, never deleting the log |
| T-04-04-06 | Tampering | `actions/cache`, including `setup-python`'s `cache:` input | mitigate by omission | Neither is used. A cache restore writes content into the workspace that no reviewer read and that the following steps execute, keyed by something a branch can influence. Measured against it: `make verify-offline` is 1 m 5 s and the install is a handful of wheels, so the saving is seconds. The test asserts `actions/cache` appears nowhere and that no step passes a `cache:` input |
| T-04-04-07 | Spoofing / repudiation | A green CI run that verified nothing | mitigate | No `continue-on-error`, no `\|\| true`, no `; true`, no `set +e`, no `exit 0`, and no pipe on the make line — a pipeline takes the status of its last command, which is the Makefile header's own argument reproduced in YAML. `_flattening` reads a comment-stripped view so the file's own explanation of these constructs cannot satisfy the rule, and every one of them is watched failing as a corruption test. The `PASS (OFFLINE — …)` wording is preserved rather than flattened to `PASS`, so a run that checked no retailer does not read like one that did |
| T-04-04-08 | Denial of service (third party) | Live retailer requests from GitHub IP ranges | mitigate | The workflow runs `make verify-offline` and the test asserts the make target set is exactly `{verify-offline}` — extracted as a token, so `verify` cannot pass by being a prefix of `verify-offline`. Six retailers times pull-request frequency from a cloud provider's ranges is exactly the trade `docs/retailer-evidence.md` argues against and the pacing and backoff work was built to avoid |
| T-04-04-09 | Denial of service (self) | A hung job on a solo maintainer's Actions minutes | mitigate | `timeout-minutes: 15` against a measured 1 m 5 s locally plus Task 1's container timing. The default is six hours. The test asserts a timeout exists and is modest |
| T-04-04-10 | Elevation of privilege / licence contamination | Installing `.[browser]` in CI | mitigate | The install line is `.[dev]`; `[browser]` and `nodriver` appear nowhere in the comment-stripped file, and a corruption test watches the rule bite on `.[browser]`. AGPL-3.0 against an MIT project is a recorded maintainer decision dated 2026-08-02, and under `--offline` the control check exits 3 before the browser rung is reached, so nothing is lost by its absence |
| T-04-04-11 | Information disclosure | `.github/` entering the published sdist | mitigate | `prune .github` in `MANIFEST.in`. 04-02's `_unpruned_directories` is the gate, and Task 2 watches it fire on `.github` before satisfying it — the first new top-level directory since that rule landed |
| T-04-04-12 | Elevation of privilege | 04-05's publish workflow blurring the boundary | mitigate | The boundary is stated as a rule rather than as prose: high privilege — `id-token: write` for PyPI Trusted Publishing, or any `write` grant — is permitted only in a workflow that no pull request can trigger. `_pr_triggered_privilege` enumerates every file in `.github/workflows/` and is exercised in both directions against a synthetic tag-triggered publish workflow, so 04-05 inherits a red test rather than a paragraph |
| T-04-04-SC | Tampering | pip / npm / cargo installs | mitigate | This plan introduces **no** new package. CI's only install is `pip install -e '.[dev]'`, audited in 04-02 and 04-03. Its build isolation does fetch an unpinned `setuptools>=77` from PyPI: **accepted**, because it is the identical surface every contributor's install already has, and pinning build dependencies in CI alone would make CI verify something nobody runs. The third-party code this plan does introduce is two GitHub Actions, handled under T-04-04-03 and audited in `<package_legitimacy_audit>`. Wanting to install anything else is a scope error — stop and re-plan |
