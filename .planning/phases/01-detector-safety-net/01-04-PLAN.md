<objective>
Build one command that answers "is bot-y actually working" with an exit code
rather than an opinion.

Purpose: GSD's verifier is an LLM forming a judgement, and a judgement can be
confidently wrong in the same direction as the code that produced it. Every
phase from here states its success criteria in terms of `make verify`, so
verification becomes reading an exit code. It also outlives the tooling — this
is the command Dan runs in six months to find out whether the thing still
works, with no agent in the loop.

Output: a Makefile with a `verify` target, plus the two checks that cannot be
expressed as plain test invocations.
</objective>

Write `scripts/control_check.py`, a script that loads `config/products.yaml`, runs one check cycle over ONLY the watches where `control` is true, and exits 0 if every control reports IN_STOCK, non-zero otherwise.

This is the one check in `make verify` that touches the network, deliberately —

is always in stock.

<task type="auto">
  <name>Task 2: Mutation check</name>
  <files>scripts/mutation_check.py</files>
  <read_first>boty/parse.py, tests/test_parse.py, tests/test_retailers.py</read_first>
  <action>
Write `scripts/mutation_check.py`, which proves the test suite would actually catch a broken extractor. A suite that passes is not evidence it detects anything.

Implementation, and this constraint is load-bearing: NEVER mutate the working
tree. Copy the `boty` package plus `tests/` and `pyproject.toml` into a
temporary directory (`tempfile.mkdtemp`), apply the mutation to the copy, and
run pytest there with cwd set to the temp dir. A mutation script that edits
files in place and crashes mid-run leaves the developer with a corrupted
checkout and no idea why — which is exactly the kind of silent damage this
project is built to avoid. Clean up the temp dir in a `finally`.

Apply at least these three mutations, each in a fresh copy, and require that
pytest FAILS for every one:

1. In `parse.py`, invert the availability test — change the membership check
   against `BUYABLE` so an out-of-stock offer reads as available. Catches: the
   suite does not actually assert availability values.
2. In `retailers.py`, make the no-structured-data branch return
   `Availability.OUT_OF_STOCK` instead of `UNKNOWN`. Catches: the single most
   important negative assertion in the project.
3. In `retailers.py`, make `_pick` ignore `first_party_only` and always return
   the first offer. Catches: the seller filter is not really tested.

If any mutation SURVIVES (pytest passes with corrupted code), exit non-zero and
report which one, because that names a specific hole in the suite.

Print a summary line: "mutation check: N/N mutations caught".
  </action>
  <verify>.venv/bin/python scripts/mutation_check.py; echo "exit=$?"; git status --porcelain boty/ | head</verify>
  <acceptance_criteria>
    - scripts/mutation_check.py contains "mkdtemp" and a finally-block cleanup
    - Running it leaves `git status --porcelain boty/` empty
    - It applies at least 3 distinct mutations
    - It exits non-zero if any mutation survives, naming which
  </acceptance_criteria>
  <done>The suite is proven to detect three specific breakages, with no risk to the working tree.</done>
</task>

<task type="auto">
  <name>Task 3: Fixture staleness warning</name>
  <files>scripts/control_check.py</files>
  <read_first>boty/fixtures.py</read_first>
  <action>
Add a `--fixtures` mode to `scripts/control_check.py` (or a small separate function invoked by the Makefile) that iterates `boty.fixtures.list_fixtures()` and prints a warning for any fixture whose `age_days` exceeds 90.

This WARNS, it does not fail. A stale fixture is a prompt to re-capture and see
whether expected values changed — and if they did, that is a real signal about
the retailer rather than a chore. Failing the build on age would train people
to re-capture blindly, which converts a signal into noise.

If a sidecar is missing or unparseable, warn about that too — an unlabelled
fixture is not much better than no fixture.
  </action>

<task type="auto">
  <name>Task 4: The Makefile</name>
  <files>Makefile</files>
  <read_first>scripts/control_check.py, scripts/mutation_check.py, pyproject.toml</read_first>
  <action>
Write a Makefile with these targets:

- `test` — pytest over tests/
- `types` — mypy
- `controls` — scripts/control_check.py
- `mutation` — scripts/mutation_check.py
- `fixtures` — the staleness warning
- `verify` — runs test, types, fixtures, controls, mutation in that order
- `verify-offline` — same but passes `--offline` to the control check, for CI
- `help` — default target, lists the above

Ordering matters: cheap and offline first (tests, types), so a developer with a
plain syntax error gets told in seconds rather than after a network round-trip.

`verify` must propagate failure. Use `set -e` semantics — each recipe line its
own command, no `|| true` anywhere. Print a final `VERIFY: PASS` or
`VERIFY: FAIL` line, and ensure the FAIL path exits non-zero. A verify target
that prints FAIL and exits 0 is worse than no verify target at all.

Use `.venv/bin/python -m` prefixes so it works without an activated venv, and
declare `.PHONY` for all targets.
  </action>
  <verify>make verify; echo "exit=$?"</verify>
  <acceptance_criteria>
    - Makefile contains targets: test, types, controls, mutation, fixtures, verify, verify-offline, help
    - Makefile contains no "|| true"
    - `make verify` exits 0 on a healthy tree and prints "VERIFY: PASS"
    - Introducing a deliberate test failure makes `make verify` exit non-zero and print "VERIFY: FAIL"
  </acceptance_criteria>
  <done>One command, one exit code, covering everything mechanical.</done>
</task>
