<objective>
Build one command that answers "is bot-y actually working" with an exit code
rather than an opinion.

Purpose: GSD's verifier is an LLM forming a judgement, and a judgement can be
confidently wrong in the same direction as the code that produced it. Every
phase from here states its success criteria in terms of `make verify`, so
verification becomes reading an exit code. It also outlives the tooling — this
is the command Dan runs in six months to find out whether the thing still
works, with no agent in the loop.

Output: a Makefile with a `verify` target, plus the two checks that cannot be
expressed as plain test invocations.
</objective>

Write `scripts/control_check.py`, a script that loads `config/products.yaml`, runs one check cycle over ONLY the watches where `control` is true, and exits 0 if every control reports IN_STOCK, non-zero otherwise.

This is the one check in `make verify` that touches the network, deliberately —
it is the part that tests cannot do. Fixtures prove the code still parses what
it used to; only a live control proves the retailer has not changed underneath
us.

CRITICAL — do not touch shared state. `boty.service` is running right now with
`WorkingDirectory` at the repo root and `state_path: state.json`. Do NOT call

service mid-cycle. Call the checker directly per control watch and never write
state.json or the status file.

Print one line per control: retailer, name, availability, and detail. On
failure, print an explanation that a failing control means the DETECTOR is
suspect, not that the market changed — a control is chosen precisely because it
is always in stock.

Accept `--offline` which skips the whole check and exits 0 with a printed
notice, so CI (which has no business hitting live retailers) can run
`make verify` minus this step.

<task type="auto">
  <name>Task 2: Mutation check</name>
  <files>scripts/mutation_check.py</files>
  <read_first>boty/parse.py, boty/retailers.py, tests/test_parse.py, tests/test_retailers.py</read_first>
  <action>
Write `scripts/mutation_check.py`, which proves the test suite would actually
catch a broken extractor. A suite that passes is not evidence it detects
anything.

FOUR constraints, each of which the plan-checker identified as a way this can
silently prove nothing. All are mandatory.

(1) NEVER mutate the working tree. Copy `boty/`, `tests/` and `pyproject.toml`
into a `tempfile.mkdtemp()`, mutate the copy, run there. A mutation script that
edits in place and crashes mid-run leaves a corrupted checkout. Clean up in a
`finally`.

(2) RUN A BASELINE FIRST. Before any mutation, run the suite in the UNMUTATED
copy and require it to PASS. If the baseline does not pass, the sandbox is
broken — abort with a distinct error. Without this, every "mutation caught" is
really "sandbox broken" and the check reports success while proving nothing.

(3) ONLY EXIT CODE 1 COUNTS AS CAUGHT. pytest exits non-zero for several
reasons: 1 = tests failed (what we want), 2 = collection error, 4 = usage
error, 5 = no tests collected. Treating "non-zero" as caught means a temp copy
missing `tests/fixtures/` would report 3/3 caught. Map anything other than 1 to
a HARNESS ERROR and abort, naming the exit code.

(4) FORCE THE SANDBOX ONTO sys.path. `bot-y` is installed editable via a
meta-path finder carrying a hardcoded absolute path to the real package
(`__editable___bot_y_0_1_0_finder.py`). Invoke as
`subprocess.run([sys.executable, "-m", "pytest", ...], cwd=tmp, env={**os.environ, "PYTHONPATH": tmp})`.
Using `.venv/bin/pytest` would import the REAL unmutated package, every
mutation would "survive", and the check would fail permanently for the wrong
reason. Assert in the baseline that `boty.__file__` resolves under tmp.

Apply these three mutations, each to a fresh copy. Each is an exact
search/replace against the POST-ANNOTATION source (plan 01-03 runs first, so
match on text that survives annotation). If a search string is not found, that
is a HARNESS ERROR — abort naming the mutation, do not silently skip it.

  M1 parse.py — search: `raw.rsplit("/", 1)[-1] in BUYABLE`
                replace: `raw.rsplit("/", 1)[-1] not in BUYABLE`
     Catches: the suite does not really assert availability values.
  M2 retailers.py — search: `Availability.UNKNOWN,\n            detail="no structured stock data found`
                replace: same with `Availability.OUT_OF_STOCK,`
     Catches: the single most important negative assertion in the project.
  M3 retailers.py — search: `if first_party_only:`
                replace: `if False:`
     Catches: the seller filter is not really tested.

After each substitution assert the file text actually CHANGED; an unchanged
file means the anchor drifted.

Print `mutation check: N/3 mutations caught` and exit non-zero if any survived,
naming which — a survivor names a specific hole in the suite.
  </action>
  <verify>.venv/bin/python scripts/mutation_check.py; echo "exit=$?"; git status --porcelain boty/ tests/ | head</verify>
  <acceptance_criteria>
    - scripts/mutation_check.py contains "mkdtemp" and a finally-block cleanup
    - It runs an unmutated baseline and aborts if the baseline does not pass
    - It treats ONLY pytest exit code 1 as "caught"; other non-zero codes abort as harness errors
    - It sets PYTHONPATH to the temp dir and invokes pytest via "-m pytest"
    - It asserts each mutated file's text differs after substitution
    - After a run, `git status --porcelain boty/ tests/` is empty
  </acceptance_criteria>
  <done>Three specific breakages proven detectable, with no way to report success from a broken sandbox.</done>
</task>

<task type="auto">
  <name>Task 4: The Makefile</name>
  <files>Makefile</files>
  <read_first>scripts/control_check.py, scripts/mutation_check.py, pyproject.toml</read_first>
  <action>
Write a Makefile with these targets:

- `test` — pytest over tests/
- `types` — mypy
- `controls` — scripts/control_check.py
- `mutation` — scripts/mutation_check.py
- `fixtures` — the staleness warning
- `verify` — runs test, types, fixtures, controls, mutation in that order
- `verify-offline` — same but passes `--offline` to the control check, for CI
- `help` — default target, lists the above

Ordering matters: cheap and offline first (tests, types), so a developer with a
plain syntax error gets told in seconds rather than after a network round-trip.

`verify` must propagate failure AND print a verdict. These conflict under make's
default semantics: make aborts the recipe on the first failing line, so a naive
`verify` can never reach a `VERIFY: FAIL` echo. Do NOT reach for `-` or
`|| true` to work around it — that breaks the exit code, which is the whole
point.

Use an explicit failure trap per step:
`@$(MAKE) test || { echo "VERIFY: FAIL (tests)"; exit 1; }`
and similarly for each subsequent step, with a final `@echo "VERIFY: PASS"`.
That prints a specific verdict naming the failing stage and still exits
non-zero. A verify target that prints FAIL and exits 0 is worse than none.

Use `.venv/bin/python -m` prefixes so it works without an activated venv, and
declare `.PHONY` for all targets.
  </action>
  <verify>make verify; echo "exit=$?"</verify>
  <acceptance_criteria>
    - Makefile contains targets: test, types, controls, mutation, fixtures, verify, verify-offline, help
    - Makefile contains no "|| true"
    - `make verify` exits 0 on a healthy tree and prints "VERIFY: PASS"
    - Introducing a deliberate test failure makes `make verify` exit non-zero and print "VERIFY: FAIL"
  </acceptance_criteria>
  <done>One command, one exit code, covering everything mechanical.</done>
</task>

  <action>
`boty.service` is running RIGHT NOW and has been since before this phase. It
holds the pre-Phase-1 code in memory: editing `boty/*.py` does not affect a
running `watch` process. Without this step, `make verify` would pass against the
working tree while the live monitor still executes the old code — a green check
describing something other than what is running, which is precisely the class
of false confidence this project exists to eliminate.

After the rest of the phase is green:
`sudo systemctl restart boty boty-web`

Then confirm both are active and that `served/boty/status.json` gets a fresh
`updated` timestamp within one check interval, proving the restarted process is
actually cycling rather than crash-looping.

Note the restart budget: the unit sets `Restart=always`, `RestartSec=30`,
`StartLimitBurst=5` over 300s. If the new code raises on startup, systemd will
give up after five attempts and leave the monitor DOWN. So check
`systemctl is-active boty` after the restart rather than assuming — a failed
restart is silent from the working tree's point of view.
  </action>
