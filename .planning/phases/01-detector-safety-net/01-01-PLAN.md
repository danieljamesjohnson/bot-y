<objective>
Build the tooling that captures a live retailer page to disk, and capture the
first set of fixtures.

Purpose: tests that hit live retailers are not tests — they fail when a site is
slow, they hammer someone else's servers, and they cannot run in CI. Fixtures
make the extraction layer testable offline and deterministically.

Output: a `capture-fixture` CLI subcommand, a loader, and captured fixtures for
GameStop and Walmart including the reseller case.
</objective>

  <name>Task 1: Fixture capture and load module</name>
  <files>boty/fixtures.py</files>
  <read_first>boty/fetch.py, boty/models.py</read_first>
  <action>
Create `boty/fixtures.py` with a `FIXTURE_ROOT = Path("tests/fixtures")` constant and two functions.

`capture(retailer: str, name: str, url: str) -> Path` — fetch `url` via `boty.fetch.get` (which already does TLS impersonation and raises Blocked/FetchError), write the response body to `FIXTURE_ROOT/<retailer>/<name>.html`, and write a sidecar `FIXTURE_ROOT/<retailer>/<name>.json` containing keys: `url`, `retailer`, `name`, `captured_at` (ISO-8601 UTC), `status`, `bytes`, and `note` (a free-text description of what stock state this page represented at capture time). Create parent directories as needed. Let Blocked and FetchError propagate — a failed capture must not write a truncated fixture.

`load(retailer: str, name: str) -> str` — return the HTML text. Raise FileNotFoundError with a message naming the expected path if absent. `load` must not trigger any network capability: do NOT import `boty.fetch` at module level. `capture()` imports it lazily inside its own function body, so merely importing `boty.fixtures` (as tests do) cannot reach the network.

`age_days(retailer: str, name: str) -> float | None` — read `captured_at` from the sidecar and return age in days, or None if the sidecar is missing or unparseable. Used later by `make verify` for the staleness warning.

Add `list_fixtures() -> list[tuple[str, str]]` returning (retailer, name) pairs by globbing `FIXTURE_ROOT/*/*.html`.
  </action>
  <verify>.venv/bin/python -c "from boty.fixtures import capture, load, age_days, list_fixtures; print('ok')"</verify>
  <acceptance_criteria>
    - boty/fixtures.py contains "def capture", "def load", "def age_days", "def list_fixtures"
    - boty/fixtures.py has NO module-level import of boty.fetch (grep: the import appears only indented, inside capture())
    - load() raises FileNotFoundError naming the expected path when a fixture is absent
  </acceptance_criteria>

  <files>tests/fixtures/README.md</files>
  <read_first>.planning/phases/01-detector-safety-net/01-CONTEXT.md</read_first>
  <action>
Write `tests/fixtures/README.md` explaining, for a contributor:

- What fixtures are for: catching *code* regressions, offline and deterministically
- What they are NOT for: telling you whether a retailer still works. That is what live control products do. State this explicitly — a contributor who believes green fixtures mean a working detector has exactly the false confidence this project exists to eliminate
- That fixtures are frozen deliberately and never auto-refreshed in CI, because a genuine breakage could otherwise land disguised as a fixture update
- How to capture a new one: the capture-fixture command with a worked example
- That `make verify` warns when a fixture exceeds 90 days old, and what to do about it (re-capture, then check whether the expected values in the tests changed — if they did, that is a real signal about the retailer, not a chore)
