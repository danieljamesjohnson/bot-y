  <files>tests/test_retailers.py</files>
  <read_first>boty/retailers.py, boty/models.py</read_first>
  <action>
Test `check_html` by monkeypatching `boty.retailers.get` to return a `Page` built from a fixture, so no network is involved.

Cover, with one test each:

1. GameStop GO Plus + fixture → `Availability.OUT_OF_STOCK`, price 54.99, `alertable is False`
2. GameStop PS5 fixture → `Availability.IN_STOCK`, `alertable is True` when no max_price set
3. Walmart GO Plus + fixture with `first_party_only=True` → NOT in stock, and `detail` mentions no first-party offer. This is the seller filter working
4. Walmart GO Plus + fixture with `first_party_only=False` and `max_price=80` → `Availability.IN_STOCK` but `alertable is False`, because the reseller price exceeds the ceiling. This proves the two defences are independent — either alone suppresses the listing
5. Walmart milk fixture with `first_party_only=True` → `Availability.IN_STOCK`, seller "Walmart.com"

Then the critical negative tests:

6. HTML with no structured data at all → `Availability.UNKNOWN`, and explicitly `is not Availability.OUT_OF_STOCK`. Assert the second condition separately with a message explaining why: conflating them is the silent failure the project exists to prevent
7. A fetch that raises `Blocked` → `Availability.UNKNOWN`, detail mentions blocked
8. A fetch that raises `FetchError` → `Availability.UNKNOWN`, detail mentions the failure
  </action>

<task type="auto">
  <name>Task 4: Monitor health and state tests</name>
  <files>tests/test_monitor.py</files>
  <read_first>boty/monitor.py, boty/models.py</read_first>
  <action>
Test `assess_health` and `State` with hand-built `Result` objects — no fixtures needed.

1. A retailer with a control Result that is IN_STOCK → `Health.ok is True`
2. A retailer whose control is OUT_OF_STOCK → `ok is False`, and `failing_controls` is non-empty. This is the detector-broken alarm
3. A retailer whose control is UNKNOWN → `ok is False`
4. A retailer with watches but NO control watch → `ok is False`, reason mentions no control. An unverified detector is treated as broken, deliberately

For `State`, using tmp_path for the state file:

5. First sighting of IN_STOCK → `transitioned_to_stock` returns True
6. Second consecutive IN_STOCK → returns False. Alerts are edge-triggered, not level-triggered
7. A Result with UNKNOWN → returns False AND does not overwrite the remembered value. Verify by: record IN_STOCK, then UNKNOWN, then IN_STOCK again, and assert the final call returns False. Without this, one blocked fetch would reset memory and cause a spurious duplicate alert on recovery
  </action>
