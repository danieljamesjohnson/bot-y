## BLOCKERS

### B-1. The browser rung cannot start in the shell these plans execute in
**Plans:** 03.1-02 (fatal), 03.1-03 (partial)
**Files:** `boty/browser.py:86-96`, `scripts/control_check.py:64,141,256`,
`/home/dan/.config/boty/env:10`

`BOTY_BROWSER_PATH` exists **only** in the service's `EnvironmentFile`. The
binary it points at is
`/home/dan/.cache/ms-playwright/chromium-1228/chrome-linux64/chrome` — not on
`PATH`, and not under any name in `browser._CANDIDATES`
(`google-chrome`, `google-chrome-stable`, `chromium`, `chromium-browser`,
`chrome`). Verified: `which google-chrome chromium chrome` returns nothing;
`$BOTY_BROWSER_PATH` is empty in an agent shell.

Consequences, all of them load-bearing for 03.1-02:

- 03.1-02 Task 1 step 0 requires `.venv/bin/python scripts/control_check.py` to
  exit 0 **before the first request**, and to "halt unless it exits 0". Best Buy
  is already a browser control, so in a plain shell this returns `INCOMPLETE`
  (exit 4), not 0. The plan halts on its own precondition before rendering
  anything.
- 03.1-02 Task 2/3 call `boty.browser.fetch_rendered` and
  `boty capture-fixture --browser`; both fail with the `MISSING_BINARY` gap
  string in a plain shell.
- 03.1-02 Task 3's verify begins `.venv/bin/python scripts/control_check.py &&
  …` (line 541), which will exit 4 with a *registered* Target control that never
  ran — the exact `INCOMPLETE`-is-not-green case the plan's own
  `<verification>` block forbids.
- 03.1-03 Task 1 repeats the same precondition ("halt unless it exits 0 across
  every configured retailer — which now includes Target") and its rung-3 Amazon
  attempt (shape A observation 3, shape B/C `--browser` capture) has the same
  dependency.

Only **03.1-04** carries the correct incantation
(`sudo systemd-run --pipe --quiet --uid=dan
--property=EnvironmentFile=/home/dan/.config/boty/env …`, plan 04 lines 103-106).
03.1-02 and 03.1-03 assert in `<interfaces>` that Chrome is "present on this
host" — true of the host, false of the shell — and never mention the wrapper.

**Fix:** carry 03.1-04's `systemd-run` incantation (or an explicit
`BOTY_BROWSER_PATH=…` export) into 03.1-02 Task 1 step 0, Task 2, Task 3 and
their `<automated>` verify blocks, and into 03.1-03 Task 1/Task 2 wherever the
browser rung or `control_check.py` is invoked.

### B-3. Rule 6 is satisfiable by prose, and a counterexample already ships
**Plan:** 03.1-03 Task 3
**Files:** `docs/retailer-evidence.md:1413`, `03.1-03-PLAN.md:441`

The proposed line form is
`^\*\*Refusal observed \(rung [1-3]\):\*\* .+$` — the anchor constrains only the
prefix; `.+` accepts anything. The tree *already* contains

```
**Refusal observed (rung 1):** not a block — **HTTP 200**, 314,757 B and 318,690 B
```

i.e. an anchored "refusal observation" whose body records that Target was **not**
refused. Rule 6 would count it. Since 03.1-02 flips Target to REACHABLE and rule
6 reads only REFUSED sections, this does not fail the shipped tree — but it means
the gate that is supposed to make REQ-07a mechanical can be satisfied by writing
the sentence, which is the failure mode the plan's own objective ("a rung 4
reached by not trying … is not [a genuine finding]") is written against.

Two viable fixes, either acceptable: (a) require the body to contain a status
code, a byte count or a matched `BLOCK_PHRASES` entry, and watch a
prose-only body fail; or (b) retire/rename the two existing Target lines
(`docs/retailer-evidence.md:1413,1419`) in 03.1-02 Task 3 step 5 so the anchor is
never used for a non-refusal. Option (a) is the one that makes the gate bite.

0d is **already** answered and marked `ANSWERED 2026-08-03 (Dan)` — the decision

### W-2. "Every Target reading carries extraction=DOM" is not achievable through the failure paths as written
**Files:** `boty/retailers.py:115-142`, `03.1-02-PLAN.md:33,45,365-370`

`must_haves.truths` and Task 2 step 4 require `extraction=Extraction.DOM` on
*every* `check_target_browser` path "including errors". But when the render
succeeds and the DOM reader finds nothing, the verdict is produced inside
`_verdict_from_html`, not inside `check_target_browser` — it exits at the
M2-anchored `return Result(… "no structured stock data found" …)`
(`boty/retailers.py:136-142`), which carries `rung=rung` and no extraction, i.e.
`STRUCTURED`. Task 2 step 3 only specifies the label "when it produces offers"
and says the structured path stays `STRUCTURED`; it never says what the
both-readers-empty path emits when `allow_dom=True`.

The plan's verify does not catch this: it only greps
`inspect.getsource(retailers.check_target_browser)` for `Extraction.DOM`
(`03.1-02-PLAN.md:399-400`), a different function. Task 3 step 9 requires "a copy
of the fixture with the control removed reads UNKNOWN" but does not assert its
`extraction`.

**Fix:** state explicitly that `_verdict_from_html` carries
`Extraction.DOM` on the no-offers return whenever `allow_dom=True`, and assert
it in the control-removed test.

### W-4. 03.1-04's verify reads `status.json` without producing it
**File:** `03.1-04-PLAN.md:198`

The `<automated>` block is `sudo systemd-run … make verify && python -c "…read
served/boty/status.json…"`. `make verify` does not run `boty check` and does not
write `status.json`; the file on disk may be an arbitrarily old service cycle.
The `duration_seconds < 120` and `healthy` assertions can therefore pass against
a payload that predates Target's registration entirely — which also means the
`extraction` key the plan asserts elsewhere may be absent. Task 1 step 3 *does*
run `boty check` in prose, but the gate does not. Add an explicit
`.venv/bin/boty check` (under the same `systemd-run` environment — see B-1) to
the verify chain before the read.
