## `pyproject.toml` is authoritative, and the direction is written down

Four statements, one fact. The referent is `pyproject.toml` `[project] version`, for three measured
reasons rather than by preference:

1. **It is the only one that becomes the artifact.** The wheel filename, the wheel `METADATA` and
   what `pip install bot-y==0.2.0` resolves are all derived from it. The other three are records
   *about* it.
2. **`scripts/release_check.py` already treats it as the referent** — its five-way comparison
   computes `disagree` as everything that differs from `declared`, where `declared` is pyproject's.
   Choosing a different referent here would put two disagreeing definitions of "the version" into one
   repository, which is the defect this criterion names.
3. **It is the only one of the four that is inside the sdist, inside `SANDBOX_CONTENTS`, and read by
   the build.**

So: `README.md`, `CHANGELOG.md` and `.planning/STATE.md` are each checked *against* pyproject, and
the finding text says which one moved. Never the reverse, and never a majority vote.

## Normalisation is a rule, not an implicit `startswith`

Three shapes have to be reconciled and each gets an explicit rule with its reason in the code:

- **`README.md` states a git tag**, `v` plus a full triple. Strip the leading `v`; all three
  components must match.
- **`CHANGELOG.md` states a full triple.** All three components must match.
- **`.planning/STATE.md` states a milestone line**, `v` plus two components. Strip the `v`; compare
  **only the components the milestone actually states** — `v0.2` agrees with `0.2.0` and with a
  future `0.2.7`, because a milestone names a minor line and patch releases inside it are expected
  and must not redden the tree. That leniency is stated out loud, not left to be discovered.

**And the trap that makes this a rule rather than a one-liner:** `"0.2.0".startswith("0.2")` is
`True`, and so is `"0.21.0".startswith("0.2")`. A string-prefix comparison silently accepts a
milestone that disagrees. **Compare component lists, never string prefixes**, and pin the
`v0.2` vs `0.21.0` case with its own test so the shortcut cannot be reintroduced.

## The always-on rule is `pyproject.toml` <-> `README.md`, and this corrects the outline

§ F3 measured it: the outline's proposed always-on rule reads `CHANGELOG.md`, which the mutation
sandbox does not contain, so both of its rules would skip and criterion 5 would be met by two skip
lines. 06-04 could not escape that — `CHANGELOG.md` genuinely cannot reach the sandbox and its
pairing had to be synthetic. **This plan can, and does better:** `README.md` and `pyproject.toml` are
both real shipped files, both in `SANDBOX_CONTENTS`, and the README sentence has to be edited anyway
because the roll falsifies it.

That single fact is what makes M25 possible. A mutation is only worth registering if some test
inside the sandbox goes red; with the README binding there is one, and without it there is none.

**The pairing is pinned, not promised.** An `ast` walk over this module collects every rule function
whose name starts with `_version_` and asserts each is named in the source of at least one test
carrying no skip decorator. Discovery is by naming convention rather than a hand-maintained tuple,
because 06-03's F4 records a rule escaping such a tuple silently and that is this criterion's own
defect one level up.

## Absence is a finding. A deleted statement must not pass

`_extraction_mismatch`'s *"one-directional would be worthless"* applied to a version: three of these
four rules are trivially satisfied by **removing** the statement. Delete the README sentence, delete
the CHANGELOG heading, delete the `milestone` key, and a naive comparator finds nothing to disagree
with and reports clean.

So every reader returns a value **or a named absence**, and an absence where the file is present is
reported as a finding with the file named. The only case that is not a finding is the file itself
being absent, which is the sandbox, and that is what the two skips are for — a distinction the skip
reasons state explicitly.

The classifier rule is the deliberate exception, and the reason is written down: a *removed*
classifier makes no claim, and 04-02 shipped with none on purpose. That rule polices disagreement,
not completeness.

## The classifier becomes a gate in both directions, not prose

§ F5's re-decision would otherwise be a comment that goes stale at the next bump — the exact failure
this phase exists to close, committed inside the plan closing it. So the decision lands as a rule:

- major component `0` ⇒ the classifier may not be `5 - Production/Stable` or `6 - Mature`
- major component `1` or above ⇒ the classifier may not be `1 - Planning`, `2 - Pre-Alpha`,
  `3 - Alpha` or `4 - Beta`

The second direction is **Phase 4's own recorded reasoning made executable**, not a new opinion.
Two-directional because one direction would be worthless: a rule that only stopped Production/Stable
at 0.x would be perfectly satisfied by classifying a 2.0.0 as Alpha.

**The decision itself: `Development Status :: 4 - Beta`**, and the argument to write in place is
measured rather than felt.

What refuses `5 - Production/Stable` at 0.2.0: nothing has been published (PyPI 404 for both
`bot-y` and the specific version, re-measured at execution); no tag exists locally or on the remote;
nobody but the maintainer has ever installed it; and `make verify` has failed live since 2026-08-06
in three classes. What refuses `3 - Alpha`: the monitor has run as a service against six live
retailers publishing per-cycle status, `make verify-offline` has been the phase gate since Phase 1,
and the control-product mechanism catches a broken detector rather than reporting a confident false
verdict. `4 - Beta` is the honest landing between two things that are both true.

**Name what would move it back to `5`**, so the next reader does not have to guess: a published
release someone other than the maintainer has installed, and a live `make verify` that passes.

## The roll is a correction and the file has to say so

CONTEXT's locked decision, verbatim: *"Do not treat the roll as a normal version bump; it is the
correction."* A reader who finds `0.2.0` below `1.0.0` in the changelog and `0.2.0` in a package
whose git history mentions 1.0.0 needs the reason on the page, not in a commit message. It goes in
three places: `pyproject.toml`'s comment beside the version, the `## [0.2.0]` changelog entry, and
the SUMMARY.

The outline's ownership table gives 06-05 three files. This plan touches five. Both additions are
deliberate and neither is a concurrency hazard:

- **`README.md`** — the outline assigns it to 06-01 *(prose only, not the matrix rows)*. 06-01 edits

## What this plan does NOT do

- **It does not tag and it does not publish.** No `git tag`, no push of a tag, no upload, no
  `make release-check`. The safety re-measurement is a read.
- **It does not add a Makefile stage.** Every gate here arrives through `make test`, so
  `test_the_documented_stages_are_the_stages_verify_runs` is unaffected.
- **It does not widen `SANDBOX_CONTENTS`.** Phase 4's rule for that constant — *"an entry lands in
  the same commit as the file it names, and is proven load-bearing by removal"* — could not be
  satisfied for a `CHANGELOG.md` or `.planning/` entry here, and 06-04 already rejected it at length.
- **It does not touch `scripts/release_check.py`.** It borrows one function from it and changes
  nothing.
- **It does not add a network call to any test.** The safety re-measurement is a one-time execution
  observation recorded as evidence, run as a shell command and never as a pytest test, never in
  `make verify`, and never in `make verify-offline`.
- **It does not mark REQ-20 complete.** 06-06 closes it by measuring what landed, on 04-05's and
  05-01's recorded precedent.
