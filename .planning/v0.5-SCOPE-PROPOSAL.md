# v0.5 — Adding A Watch Without Editing YAML (scope proposal)

**Status: PROPOSAL, not a scoped milestone.** Written 2026-09-11 at Dan's request. Nothing here is
committed; `REQUIREMENTS.md` and `ROADMAP.md` are untouched. Scoping it properly is
`/gsd-new-milestone`, and that should happen after Dan reacts to the shape below.

**What Dan asked for, verbatim, 2026-09-09:**

> "the problem with it for me is adding new things to track in a user friendly way. i'd like be able
> to search by product name and it give me the options and i click it and boom it's getting watched.
> simple as that."

---

## 1. The measurement that reframes this

Adding a watch today means hand-editing `config/products.yaml`. The assumption behind "search by
name" is that the hard part is *turning a name into a retailer identifier*. **Measured, it mostly
is not:**

| retailer | what `target` actually is today |
|---|---|
| amazon | a URL |
| gamestop | a URL |
| nintendo | a URL |
| target | a URL |
| walmart | a URL |
| bestbuy | a bare SKU (`6216393`) |

**Five of six already take a URL.** So for five retailers the identifier is something a person can
obtain in two seconds from their own browser's address bar. What is missing is not resolution — it
is **a way to add the watch without opening a text editor and knowing the YAML shape.**

That matters because it splits the request into a cheap half that works everywhere and an expensive
half that works almost nowhere, and lets the cheap half ship first.

## 2. The wall, stated before any design

Search is *exactly* the surface that refuses this project. This is not a guess:

- **Best Buy** — phase 10 spent three reads establishing that SKU search returns a **23,292-byte
  shell with no `<body>`**. Its search is the reason its control reads as unreadable.
- **Amazon, Target, Walmart** — all three serve a challenge page to us at rung 1, and Walmart and
  Target refuse rung 3 as well (measured 2026-08-27; escalating a rung is a disproved hypothesis,
  `ROADMAP.md` § *Why no phase here proposes escalating a rung*).

So a naive "search all six retailers by name" is **six new blocked endpoints**, four of them
blocked by the same mechanism v0.4 exists because of. A milestone that promised it would be
promising a capability this project has measured itself not to have.

**GameStop and Nintendo are the two retailers currently reading reliably.** Whether their *search*
endpoints are reachable is **NOT MEASURED** and must not be assumed by any plan — it is the first
thing v0.5 should measure, and it is cheap (two requests).

## 3. Proposed shape — three phases, cheapest first

### Phase A — Add and remove a watch without editing YAML *(no live requests)*

The half that works for every retailer and unblocks the actual friction.

- `boty add <url>` — infer the retailer from the host, extract the identifier, append a validated
  watch to `config/products.yaml`, preserving comments and ordering.
- `boty remove <name>` and `boty list`.
- Refuse with a stated reason rather than writing a broken watch: unknown host, a URL shape the
  adapter cannot read, a duplicate, or a watch that would need a store pin.
- **The YAML file stays the source of truth.** It is tracked, public and human-readable, and three
  milestones of argument live in its comments. A sidecar database would split the truth in two.

**Why this is first:** it is the whole of what Dan described *minus* search, it needs no network,
and it is testable entirely offline.

### Phase B — Search where search is reachable *(small, capped live budget)*

- **Measure first, for GameStop and Nintendo only:** does a search endpoint answer us at all? Cap
  stated, count recorded, a refusal recorded as the measurement. **If they refuse, Phase B stops
  there and says so** — that is a legitimate outcome, not a failed phase.
- If they answer: `boty search "<name>"` returns candidates (name, price, URL), you pick one by
  number, and it is added through Phase A's code path.
- **Do not attempt Amazon, Target, Walmart or Best Buy.** Their refusal is already measured, and
  spending a probe budget to re-establish it would be spending politeness on a known answer.

### Phase C — The same thing on the dashboard *(no new network surface)*

- A field on `served/boty/index.html` that calls Phase A/B, so "search, click, watched" exists
  where Dan already looks.
- `boty-web.service` currently serves the page **read-only on loopback**. Writing config from a web
  page is a genuine change in posture and needs its own decision — it is listed here so the shape
  is visible, not because it is settled.

## 4. What this proposal deliberately does NOT promise

- **Not "search by name across all six retailers."** Four of six refuse search, measured. Promising
  it would be the overclaim this project's own v0.2 milestone existed to correct.
- **Not a new datastore.** `config/products.yaml` stays authoritative.
- **Not a hosted or multi-user service.** `QUESTIONS.md`'s *"Decision I made without you"* already
  records the web-UI/plugin/hosted questions as having real design surface and being out of scope;
  that stands.
- **No claim that GameStop or Nintendo search works.** Unmeasured, and Phase B's first act is to
  find out.

## 5. Honest sequencing note

v0.4 is **not finished**: phase 11 is unstarted and needs a probe budget. Two things are also true
of the live daemon and should be weighed before starting a new milestone:

- **Best Buy does not read at all** (unrendered shell). v0.5 would add watches to a monitor that
  currently reads 2 of 6 retailers reliably.
- **The cool-off has never fired in production.** v0.4's headline behaviour is live but
  undemonstrated — live counts are `amazon` 10 and `target` 18 against a threshold of 30.

Neither blocks v0.5, and Phase A in particular is independent of all of it. But "more watches" on a
monitor that can only read two retailers is worth naming as a trade rather than discovering later.
